# Подписи стандартных реквизитов: снятие с платформы

Подписи стандартных реквизитов (`Ссылка`, `Код`, `Наименование`, `Регистратор`, `N`) ставит сама
платформа. В выгрузке их нет: узел `<xr:Synonym/>` у стандартного реквизита пуст, пока его не
переопределили, а XSD описывает только состав узлов. Поэтому словарь снимается с платформы и лежит
в ресурсах готовым файлом, руками его не ведут.

Результат: `src/main/resources/io/github/yellowhammer/designerxml/cf/standard-labels.json`,
читает его `StandardAttributeLabels`.

## Как устроено снятие

Как в [namespace-forest](https://github.com/yellow-hammer/namespace-forest): `ibcmd` создаёт файловую
ИБ и загружает в неё конфигурацию из [`src/`](src/), `ibsrv` публикует HTTP-сервис, JSON забирается
запросом. Конфигуратор не участвует, лицензия не нужна.

Конфигурация `src/` собрана из семени scaffold (`fixtures/samples-1c-platform/seed`) и дополнена
объектами тех видов, которых в семени нет: регистры, журнал документов, последовательность,
бизнес-процесс. Настройки объектов подобраны так, чтобы стандартных реквизитов было как можно
больше: справочник иерархический и с владельцем, документ проводится и нумеруется, у плана счетов
заданы порядок и виды субконто, у плана видов расчёта включены период действия и зависимость,
регистр бухгалтерии есть и с корреспонденцией, и без.

Вариант встроенного языка у конфигурации английский: имена стандартных реквизитов нужны такими же,
как их пишет формат выгрузки (`Ref`, `LineNumber`), а не в русском варианте. Язык интерфейса при
этом русский, поэтому подписи приходят по-русски.

Обход метаданных лежит в модуле сервиса
[`src/HTTPServices/ВыгрузкаПодписей/Ext/Module.bsl`](src/HTTPServices/ВыгрузкаПодписей/Ext/Module.bsl):
`GET /labels/dump` отдаёт подписи, `GET /labels/probe` отдаёт диагностику - что платформа отвечает
на отдельные выражения.

## Как повторить

Локально, с установленной платформой:

```bash
BIN="/c/Program Files/1cv8/8.5.1.1343/bin" tools/standard-labels/dump.sh
```

На CI - workflow `.github/workflows/dump-standard-labels.yml` (запуск руками): ставит платформу
указанной версии через `yard` и отдаёт готовый JSON артефактом.

Снятое на 8.5.1.1343 и на 8.3.27.2214 совпадает подпись в подпись, поэтому файл в ресурсах один,
без разбивки по версиям платформы.

## Чего платформа не отдаёт

- **Подпись `LineNumber` у табличной части.** У стандартных реквизитов табличной части
  `Синоним` и `Представление()` пустые, хотя конфигуратор пишет в заголовке колонки `N`. У регистров
  тот же `LineNumber` платформа называет `N`, у стандартных табличных частей плана счетов и плана
  видов расчёта - `Номер строки`. Запись для табличной части в `StandardAttributeLabels` остаётся
  сверенной с конфигуратором.
- **Стандартные команды.** Ни свойства `СтандартныеКоманды` у объекта метаданных, ни функции
  вроде `ПолучитьСтандартныеКоманды` в платформе нет: `Поле объекта не обнаружено (StandardCommands)`,
  `Процедура или функция с указанным именем не определена (GetStandardCommands)`. Автозаполненную
  командную панель можно было бы прочитать из формы, которую платформа строит сама, но
  `ПолучитьФорму` в сеансе HTTP-сервиса недоступна, а менеджер объекта отвечает
  `Интерактивные операции недоступны`: генерация формы требует интерактивного сеанса, то есть
  лицензии.
- **Счета регистра бухгалтерии с корреспонденцией.** У регистра с корреспонденцией платформа не
  перечисляет ни `Account`, ни `AccountDr`/`AccountCr`: в `СтандартныеРеквизиты` их просто нет.
  Без корреспонденции `Account` есть.
