# Эталоны выгрузки: съёмка с платформы

Эталоны `fixtures/samples-1c-platform/snapshots/<формат>/` - источник правды для scaffold
(см. [docs/scaffold-golden.md](../../docs/scaffold-golden.md)): значения по умолчанию, порядок
свойств и форма записи берутся только с платформы, из XSD их не вывести. Инструмент снимает эталоны
с платформы нужной версии через `ibcmd`: конфигуратор и лицензия не нужны, поэтому съёмка идёт и
локально, и на CI.

## Что снимается

Результат раскладывается как в submodule: `<OUT>/<формат>/...`. Формат определяется по атрибуту
`version` выгрузки, `ConfigDumpInfo.xml` не сохраняется. Рядом, в `<OUT>/summary-<версия>.txt`,
лежит сводка: что снято и каким путём (в эталоны она не входит).

| Каталог | Что это | Как снято |
|---|---|---|
| `cf-empty-infobase/` | конфигурация новой пустой ИБ: режим совместимости = версия платформы, `UsePurposes` = `PlatformApplication`, язык Русский | `infobase create --locale=ru`, сразу `config export` |
| `cf-bare-objects/` | голый объект каждого вида верхнего уровня, `Configuration.xml`, `Languages/Русский.xml`, а также `Ext` там, где платформа его выгружает: права роли, форма общей формы, описание WS-ссылки | семя [`seed/`](seed/), см. «Маршрут» |
| `cf-object-nodes/` | объект-владелец каждого вида с узлом каждого вида, который добавляет md-sparrow: реквизит, табличная часть (пустая и с реквизитом), команда, значение перечисления, измерение, ресурс, признаки учёта; внешние отчёт и обработка - в `ExternalReports/` и `ExternalDataProcessors/` | семя [`seed/`](seed/) с узлами, см. «Узлы объектов» |
| `cfe-empty/` | пустое расширение: `Configuration.xml` и роль по умолчанию | `config extension create --name=ПустоеРасширение --name-prefix=пр --purpose=add-on` в пустой ИБ, `config export --extension` |
| `external-files/empty/` | голые `ВнешнийОтчет1` и `ВнешняяОбработка1` | [`seed-external/`](seed-external/): `config import --out=<файл>`, затем `config export --file=<файл>` |
| `external-files/empty-full-objects/` | внешние отчёт и обработка с формами и модулями | `.epf`/`.erf` из эталона 2.20 собирает платформа 8.3.27+, разбирает платформа нужной версии |

Виды новее формата платформы не снимаются: `Bot` появился в 2.11, `WebSocketClient` в 2.20,
`PaletteColor` в 2.21.

UUID в `cf-bare-objects`, `cf-object-nodes` и `external-files` берутся из семени, поэтому повторная съёмка даёт те же
байты. В `cf-empty-infobase` и `cfe-empty` UUID выдаёт платформа, и они каждый раз новые: такие
эталоны сравнивают с точностью до UUID.

## Как запустить

Нужны платформа с `ibcmd` и Python 3 (только стандартная библиотека).

Локально, Windows и Git Bash:

```bash
BIN="/c/Program Files/1cv8/8.5.1.1343/bin" tools/golden-snapshots/dump.sh
# старой платформе .epf/.erf с формами собирает новая:
BIN="/c/Program Files/1cv8/8.3.23.2040/bin" BUILDER_BIN="/c/Program Files/1cv8/8.3.27.2214/bin" \
  tools/golden-snapshots/dump.sh
```

`dump.sh nodes` снимает только `cf-object-nodes`, остальное в `<OUT>/<формат>` не трогает (сводка -
`summary-<версия>-nodes.txt`).

Результат по умолчанию - `tools/golden-snapshots/out/` (в git не попадает). Переменные окружения
описаны в начале [`dump.sh`](dump.sh): `OUT`, `WORK`, `PYTHON`, `EXT_BIN`, `BUILDER_BIN`,
`EXT_FULL_SRC`, `VERIFY_ROUTES`, `KEEP_WORK`. Коды выхода: `0` - снято всё, что умеет эта версия
`ibcmd` (пропуски из-за версии только отмечаются в сводке), `1` - платформа отвергла семя или ничего
не снято, `3` - часть эталонов не снята из-за ошибки или сверка маршрутов не сошлась (подробности
в сводке).

На Windows `ibcmd` падает с «Ошибка при работе с файлом», если путь к базе длиннее ~250 символов:
рабочий каталог по умолчанию - короткий временный, длинный `WORK` задавать не надо. Кириллица
в аргументах из Git Bash доходит до `ibcmd` без искажений.

Сверить снятое с эталонами submodule:

```bash
python3 tools/golden-snapshots/snapshot.py compare \
  tools/golden-snapshots/out/2.21/cf-bare-objects fixtures/samples-1c-platform/snapshots/2.21/cf-bare-objects
python3 tools/golden-snapshots/snapshot.py compare --uuid \
  tools/golden-snapshots/out/2.21/cfe-empty fixtures/samples-1c-platform/snapshots/2.21/cfe-empty
```

На CI - workflow [`golden-snapshots.yml`](../../.github/workflows/golden-snapshots.yml), запуск руками
с версиями платформы через пробел. Платформу ставит композитное действие
[`setup-1c-platform`](../../.github/actions/setup-1c-platform/action.yml) (yard и `.run`/`.deb`, как
в namespace-forest), секреты `ONEC_LOGIN`/`ONEC_PASSWORD`. Отдельная задача один раз собирает
`.epf`/`.erf` платформой `builder_version` (`dump.sh build-external`), задачи матрицы (не больше трёх
сразу) снимают эталоны и отдают артефакт `snapshots-<версия>`. Если задан `edt_version`, эталоны
импортируются в проекты 1C:EDT (артефакт `edt-<версия EDT>`; EDT нужна Java 17, см. ниже).

Импорт в EDT делает [`edt-import.sh`](edt-import.sh). **EDT CLI требует Java 17**: с другой
версией (например 21) `1cedtcli` показывает модальное окно «Неподдерживаемая Java» и ждёт ответа.
На CI JDK 17 ставит `actions/setup-java`, а путь к `java` передаётся `1cedtcli` ключом `-vm`
(переменная `EDT_JAVA`, по умолчанию `$JAVA_HOME/bin/java`; скрипт проверяет, что это 17).
Скрипт рассчитан на CI: на рабочей машине с графическим сеансом каждый запуск `1cedtcli` поднимает
окно EDT на рабочем столе, поэтому локально его запускать не стоит.

```bash
EDTCLI=/opt/1C/1CE/components/1c-edt-2026.1.2+.../1cedtcli EDT_JAVA=/usr/lib/jvm/temurin-17/bin/java \
  SNAPSHOTS=tools/golden-snapshots/out FORMATS=2.21 xvfb-run -a tools/golden-snapshots/edt-import.sh
```

Каждый `import` - отдельный запуск `1cedtcli`: в одном сеансе EDT 2026.1 следующая команда после
импорта может зависнуть. Внешние объекты импортируются без базового проекта: с ним EDT не находит
открытый проект.

## Маршрут съёмки голых объектов

Проверка конфигурации при обычной загрузке не пропускает голыми 14 видов: регистрам нужны ресурс
или измерение и регистратор, подписке на событие - источник, событие и обработчик и так далее.
Поэтому объекты грузятся с минимальными зависимостями, а после выгрузки зависимости срезаются:

1. Выгружается пустая ИБ: так определяется формат (и снимается `cf-empty-infobase`).
2. `snapshot.py assemble` собирает семя под формат: из [`seed/`](seed/) убираются виды новее
   формата, файлы 14 видов заменяются версиями из [`seed-deps/`](seed-deps/), в состав добавляются
   вспомогательные объекты `ВспомогательныйДокумент`, `ВспомогательныйМодуль`,
   `ВспомогательнаяКонстанта`. Ссылки вспомогательного объекта на виды, которых в прогоне нет,
   убираются.
3. Обычный `config import` с проверкой, затем `config export`.
4. `snapshot.py finish` убирает вспомогательные объекты и их строки в `ChildObjects` конфигурации,
   а у 14 видов возвращает добавленные свойства к пустому элементу (`<Namespace/>`) и дочерние
   объекты к `<ChildObjects/>`. Что срезать, скрипт определяет сам, сравнивая файл из `seed-deps/`
   с файлом из `seed/`: таблицы в коде нет.
5. Сверка маршрутов (`VERIFY_ROUTES=1`, если в `ibcmd` есть `import files --no-check`): семя без
   зависимостей грузится в другую ИБ в две фазы - конфигурация с языком обычным `config import`,
   затем все файлы через `config import files --no-check` - и выгрузка сравнивается с шагом 4
   побайтно. На 8.3.23, 8.3.24, 8.3.27 и 8.5.1 совпадают все файлы.

| Вид | Чего требует проверка | Что добавлено в `seed-deps/` |
|---|---|---|
| WebService | пространство имён | `Namespace` = `urn:seed` |
| HTTPService | корневой URL | `RootURL` = `seed` |
| EventSubscription | источник, событие, обработчик | `Source` = `cfg:CatalogObject.Справочник1`, `Event` = `BeforeWrite`, `Handler` в `ВспомогательныйМодуль` |
| ScheduledJob | имя метода | `MethodName` в `ВспомогательныйМодуль` (текст модуля не нужен) |
| FunctionalOption | хранение | `Location` = `Constant.ВспомогательнаяКонстанта` |
| FunctionalOptionsParameter | использование | `Use` = `Catalog.Справочник1` |
| CommonCommand | группа | `Group` = `ActionsPanelTools` |
| InformationRegister | измерение, ресурс или реквизит | измерение `Измерение1` |
| AccumulationRegister | ресурс и регистратор | ресурс `Ресурс1`, регистратор `ВспомогательныйДокумент` |
| AccountingRegister | ресурс и регистратор (план счетов не нужен) | ресурс `Ресурс1`, регистратор `ВспомогательныйДокумент` |
| CalculationRegister | план видов расчёта и регистратор (ресурс не нужен) | `ChartOfCalculationTypes` = `ПланВидовРасчета1`, регистратор `ВспомогательныйДокумент` |
| DocumentJournal | регистрируемые документы | `RegisteredDocuments` = `ВспомогательныйДокумент` |
| Sequence | документы | `Documents` = `ВспомогательныйДокумент` |
| BusinessProcess | задача | `Task` = `Task.Задача1` |

Запасные пути. Если обычный `config import` отверг семя, а `import files --no-check` в `ibcmd` есть,
все виды снимаются двухфазным маршрутом без проверки; в сводке это помечено. Если `--no-check` нет,
виды, чьи объекты названы в строках `[ERROR]` журнала, исключаются, остальное снимается, а
исключённые попадают в сводку как не снятые (код выхода 3). Если платформа отвергла семя и так,
скрипт падает с журналом импорта.

## Узлы объектов

`cf-object-nodes` - эталон дочерних узлов для md-sparrow (см. [docs/scaffold-golden.md](../../docs/scaffold-golden.md#дочерние-узлы)).
`snapshot.py assemble --nodes` берёт из [`seed/`](seed/) только виды, у которых такие узлы бывают по
схеме (`<Вид>ChildObjects` XSD, от 2.10 до 2.21 не меняется), и заменяет их `ChildObjects` узлами.
Узел в семени минимальный: имя, синоним на русском, пустой комментарий,
тип - строка 10 (у признаков учёта - булево), у команды группа `FormCommandBarImportant`. Остальные
свойства дописывает платформа, это и есть эталон узла. Табличных частей две: пустая (эталон новой
табличной части) и с реквизитом (эталон реквизита табличной части). UUID узлов - `uuid5` от имён
владельца и узла, поэтому повторная съёмка даёт те же байты.

| Вид | Узлы |
|---|---|
| `Catalog`, `Document`, `DataProcessor`, `Report`, `ChartOfCharacteristicTypes`, `ChartOfCalculationTypes`, `ExchangePlan`, `Task`, `BusinessProcess` | реквизит, две табличные части, команда |
| `ChartOfAccounts` | то же и признак учёта, признак учёта субконто |
| `Enum` | значение, команда |
| `DocumentJournal`, `FilterCriterion` | команда |
| `InformationRegister`, `AccumulationRegister`, `AccountingRegister`, `CalculationRegister` | измерение, ресурс, реквизит, команда |
| `Sequence` | измерение |
| `ExternalReport`, `ExternalDataProcessor` | реквизит, две табличные части |

Маршрут тот же, что у голых объектов: владельцы с зависимостями из [`seed-deps/`](seed-deps/)
(регистратор, задача бизнес-процесса, документы журнала и последовательности), обычный
`config import` с проверкой, выгрузка, срезка зависимостей и сверка с маршрутом
`import files --no-check`. Конфигурация и язык в набор не входят: они такие же, как в
`cf-bare-objects`. Вне `ChildObjects` объекты конфигурации совпадают с `cf-bare-objects` байт в байт. Внешние
отчёт и обработка собираются из [`seed-external/`](seed-external/) с узлами (`config import --out`) и
разбираются `config export --file`. На 8.3.23, 8.3.24, 8.3.27 и 8.5.1 снимается всё, маршруты
совпадают побайтно, повторная съёмка даёт те же файлы.

Порядок узлов в выгрузке задаёт платформа, а не семя: семя пишет измерение, ресурс и реквизит
регистра, а платформа выгружает регистры сведений, накопления и расчёта как ресурс, реквизит,
измерение - в порядке схемы.

## Семя

- **Версия 2.10.** Всё семя объявлено `version="2.10"`: XML новее своего формата платформа
  отвергает («Неизвестная версия формата»), а выгрузка от объявленной версии не зависит. Поэтому
  одно семя годится для всех платформ.
- **Минимум.** У объекта - `Name`, `InternalInfo` с полным набором `GeneratedType` (сама платформа
  их не создаёт; у плана обмена нужен ещё `xr:ThisNode`) и `<ChildObjects/>` у видов с дочерними
  объектами. У `Configuration.xml` - ровно 7 `xr:ContainedObject` с фиксированными `ClassId`
  («Узлов ContainedObject должно быть 7»), имя `ЭталонСемя` и язык. Всё остальное платформа
  заполняет своими умолчаниями XML.
- **UUID фиксированы.** У 19 видов, эталоны которых уже были, а также у конфигурации и языка -
  UUID существующих эталонов, включая `TypeId`/`ValueId`. У новых видов - детерминированные
  `uuid5`. Поэтому выгрузка совпадает с прежними эталонами байт в байт.
- **Значения не по умолчанию** нужны только затем, чтобы совпасть с прежними эталонами: те сняты из
  семени, которое записал md-sparrow.
  - `Catalog`: синоним и пять представлений (`ObjectPresentation`, `ExtendedObjectPresentation`,
    `ListPresentation`, `ExtendedListPresentation`, `Explanation`) = «Справочник1»;
  - `CommonModule`: `Server=true`, `ClientOrdinaryApplication=false` (умолчание XML - наоборот);
  - `Language`: синоним «Русский»;
  - `Configuration`: `<UsePurposes/>`, `DefaultLanguage`, `CompatibilityMode=Version8_3_12`.
    Умолчания XML здесь другие (`PlatformApplication` и версия платформы) - их показывает
    `cf-empty-infobase`. `ConfigurationExtensionCompatibilityMode` платформа из XML не берёт и
    всегда пишет свою версию;
  - `Role`: минимальный корневой `<Rights/>` в `Ext/Rights.xml`. Платформа дописывает три флага по
    умолчанию, а без этого файла права не выгружает.
- **Новые виды** - умолчания платформы, кроме двух:
  - `CommonForm`: `FormType=Managed` (умолчание XML - `Ordinary`) и `Ext/Form.xml` с пустым корнем
    `<Form xmlns="http://v8.1c.ru/8.3/xcf/logform" version="2.10"/>`. Опыт на 8.5.1 и 8.3.23: без
    `Form.xml` платформа выгружает только метаданные формы, содержимого нет. Из пустого корня она
    пишет `<AutoCommandBar name="" id="-1"/>` и `<Attributes/>` - пустую управляемую форму, как у
    форм внешних объектов в эталоне 2.20. Заданное имя командной панели (например
    `ФормаКоманднаяПанель`, как в ssl31) платформа сохраняет, но своих значений в семя не кладём.
    EDT при импорте называет эту панель `FormCommandBar`;
  - `WSReference`: `Ext/WSDefinition.xml` с пустым `<definitions xmlns="http://schemas.xmlsoap.org/wsdl/"/>`.
    Обычный импорт обходится и без него, но тогда не выгружает описание, а `import files` без него
    ложно жалуется на соседние объекты. Платформа переписывает файл в своё пустое описание.
- **Не входят** `Language` (язык уже есть) и устаревший `Interface`. Другие `Ext` (модули, макеты,
  картинки, стиль, пакет XDTO) проверке не нужны, и без них платформа их не выгружает.

Семя статично, UUID в нём менять нельзя: иначе эталоны разойдутся с прежними. Новый вид
добавляется файлом в `seed/` (и строкой в `ChildObjects` семени), а если проверка его голым не
пропускает, ещё файлом с минимальной зависимостью в `seed-deps/`.

## Внешние объекты и расширение

- `seed-external/` - минимальный XML с UUID эталона 2.20: `InternalInfo` с `ContainedObject` и
  `GeneratedType`, `Name`, `<ChildObjects/>`; остальные свойства платформа дописывает сама.
  `config import --out` принимает только путь к корневому XML (на каталог: «Отсутствует контейнер
  метаданных»). `config export --file` пишет в существующий каталог, а если его нет - в файл
  `<каталог>.xml`.
- `empty-full-objects` собирается из эталона 2.20 (`EXT_FULL_SRC`), а его XML читают только
  платформы 8.3.27+. Файлы `.epf`/`.erf` между версиями переносимы: 8.3.23 разбирает файл,
  собранный 8.5.1, так же, как свой. Порядок выбора: готовые файлы из `EXT_BIN`, сборка своей
  платформой (формат 2.20+), сборка платформой из `BUILDER_BIN`; иначе пропуск с сообщением. Объекты
  внутри называются `ВнешнийОтчет2`/`ВнешняяОбработка2`, раскладка как в эталоне:
  `<каталог>/<каталог>.xml`.
- Пустое расширение создаётся с `--purpose=add-on`: без него получается `Customization`.
  `--name-prefix` для `ibcmd` обязателен, но в выгрузку не попадает (`NamePrefix` пустой). Режим
  совместимости расширения берётся из основной конфигурации пустой ИБ, то есть равен версии
  платформы. Выгрузка расширения пробуется при любом коде `extension create`: 8.3.20 создаёт
  расширение, но отменяет обновление конфигурации БД и возвращает ненулевой код. Если в `ibcmd` нет
  `extension create` или выгрузить расширение не удалось, оно загружается из
  [`seed-cfe/`](seed-cfe/): `config import --extension=ПустоеРасширение`. На 8.3.23 результат
  совпадает с `extension create` с точностью до UUID (при этом `extension info` показывает
  `purpose: customization` - это свойство регистрации в ИБ, на XML оно не влияет).

## Ограничения по версиям

- **8.3.23 и новее (2.16+)** - снимается всё. Проверено локально на 8.3.23.2040, 8.3.24.1691,
  8.3.27.2214 и 8.5.1.1343, на CI - на 8.3.25.1633 и 8.3.26.1656.
- **8.3.20-8.3.22 (2.13-2.15)** - `extension create` есть (команда `infobase config extension`
  появилась в 8.3.20). У 8.3.20 она завершается с кодом 102 (обновление конфигурации БД отменено),
  но расширение создаёт: скрипт его выгружает, а если не выйдет - берёт запасной путь из `seed-cfe/`.
  Загрузить расширение с ролью через `config import --extension` 8.3.20 не может вовсе, даже его
  собственную выгрузку.
  `import files --no-check` тоже есть, сверка маршрутов совпадает побайтно. Внешние объекты
  пропускаются с сообщением в сводке: сборка и разборка `.epf`/`.erf` через `ibcmd` работают только
  с 8.3.23. Проверено на CI: 8.3.20.2290, 8.3.21.1895, 8.3.22.2557.
- **8.3.17-8.3.19 (2.10-2.12)** - режима расширений в `ibcmd` нет, расширение снимается запасным
  путём из `seed-cfe/`; `import files --no-check` тоже нет, маршруты не сверяются. Внешние объекты
  пропускаются, как и у 8.3.20-8.3.22. У 8.3.19 нет ключа `--data`, ИБ создаётся без него.
  Проверено на CI: 8.3.17.2760, 8.3.18.1959, 8.3.19.1770.
- Язык процесса: на Linux скрипт ставит `ru_RU.UTF-8`, если такая локаль есть (от языка зависят имена
  по умолчанию у расширения). На Windows язык `ibcmd` не меняется.

## Проверка загрузкой

[`roundtrip.py`](roundtrip.py) проверяет сам md-sparrow на платформе: всё, что он пишет в формате этой
платформы, `ibcmd` загружает и выгружает теми же байтами. Формат берётся из выгрузки пустой базы.

```bash
python3 tools/golden-snapshots/roundtrip.py --jar build/libs/md-sparrow-<версия>-all.jar --bin <каталог ibcmd>
```

| Сценарий | Что пишет md-sparrow | Как загружается |
| --- | --- | --- |
| `forms` | десять видов с формами из `cf-form-add` и `cf-form-compile` с основным реквизитом, общая форма | `config import` с проверкой |
| `extension` | расширение к этой конфигурации: свой справочник и заимствованный | `config import --extension` |
| `external` | внешние отчёт и обработка с формами | `config import --out`, `config export --file` (8.3.23+) |
| `all-kinds` | объекты всех видов формата с дочерними узлами | язык обычным `config import`, остальное `import files --no-check` (8.3.20+) |

Каждый записанный файл сверяется с выгрузкой побайтно; файл, который платформа выгрузила сверх
записанного, тоже различие (кроме `ConfigDumpInfo.xml`). `ibcmd` 8.3.20 не загружает расширение с ролью
через `config import --extension` даже из выгрузки расширения, созданного им самим («Роль.ОсновнаяРоль -
Дублирование имени»): скрипт проверяет это контрольной загрузкой и, если все ошибки отказа те же, что у
контроля, помечает сценарий `extension` как ограничение платформы (`platform`), а не различие; любая
другая ошибка - отказ файлов md-sparrow. Рабочий каталог `--work` скрипт стирает, поэтому он должен быть
пустым, новым или оставленным прошлой проверкой. Отчёт с различиями - `report.txt` и
`summary.json` в `--out`; код выхода 1 - есть различия или платформа отвергла файлы. В workflow
`golden-snapshots` проверка включена по умолчанию (`roundtrip`) и идёт на той же платформе, что и
съёмка; снимать эталоны при этом необязательно (`snapshots`).
