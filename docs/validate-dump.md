# Проверка выгрузки (`validate-dump`)

Проверяет, цела ли выгрузка конфигурации или расширения: то, что можно установить по самим файлам,
без запуска платформы. Результат - JSON-список находок; пустой список означает, что выгрузка цела.

```
validate-dump path/to/src/cf
```

Та же операция через канал параметров (кириллические пути в `argv` на Windows не выживают):

```json
{ "op": "cf-validate-dump", "cfRoot": "C:/проект/src/cf" }
```

```
read-json --params params.json
```

## Находки

У каждой находки есть путь относительно корня выгрузки, тип и имя объекта, вид проблемы и текст.
Вид (`kind`) стабилен, по нему удобно фильтровать и раскладывать по важности.

| `kind` | Что означает |
| --- | --- |
| `configuration-missing` | нет `Configuration.xml`: каталог не похож на выгрузку |
| `version-unsupported` | версия формата выгрузки не поддерживается, дальше проверять нечем |
| `missing-file` | объект объявлен в составе, файла нет |
| `orphan-file` | файл объекта есть, в составе не объявлен |
| `duplicate-entry` | объект объявлен в составе дважды |
| `unknown-type` | тип объекта неизвестен формату выгрузки: его нет в схеме этой версии |
| `child-objects-order` | типы в составе идут не в том порядке, в каком их пишет платформа |
| `version-mismatch` | версия формата у объекта отличается от версии конфигурации |
| `version-unreadable` | у файла объекта не читается версия формата: файл не похож на выгрузку объекта |
| `dangling-reference` | ссылка вида `Role.ПолныеПрава` ведёт на объект, которого нет |
| `dump-info-version` | версия формата в `ConfigDumpInfo.xml` отличается от версии конфигурации |
| `dump-info-extra` | в `ConfigDumpInfo.xml` записан объект, которого в выгрузке нет |

Ссылки проверяются в `Configuration.xml` и в составах подсистем. Ссылка считается целой, если объект
есть на диске: вложенные подсистемы в состав конфигурации не входят, но ссылаться на них можно.
`ConfigDumpInfo.xml` проверяется, только если он есть в выгрузке.

## Что не проверяется

**Порядок объектов внутри одного типа.** Конфигуратор сортирует имена своим сравнением: числа в именах
сравниваются как числа (`EnterpriseData_1_2_3` идёт раньше `EnterpriseData_1_20_2`), а в типовых выгрузках
встречаются и другие расхождения с алфавитным порядком. Проверка по алфавиту дала бы находки на здоровых
конфигурациях, поэтому её нет.

**Содержимое объектов.** Схему проверяет команда `validate` (см. [ниже](#проверка-файла-по-xsd-validate)),
эта операция смотрит на выгрузку целиком.

Версию формата читает тот же код, что и остальные операции инструмента, - по корневому элементу
`MetaDataObject`. Если у файла объекта её не прочитать, это отдельная находка, а не молчаливый
пропуск.

## Как читается состав

Состав берётся из текста `Configuration.xml`, а не через JAXB: модель отдаёт объекты в порядке схемы и
молча выбрасывает неизвестные элементы, то есть ровно то, что проверка и должна увидеть. Версия формата
читается с корневого элемента файла.

## Проверено на выгрузках

Находок нет на типовой большой конфигурации, на демонстрационной конфигурации БСП и на выгрузке
расширения. Каждый вид находки закрыт тестом на намеренно испорченной выгрузке
(`CfDumpValidationTest`), а сама выгрузка для тестов собирается тем же кодом, которым инструмент
создаёт конфигурацию и объекты.

## Проверка файла по XSD (`validate`)

```
validate path/to/src/cf/Catalogs/Валюты.xml resources/namespace-forest -v V2_20
```

Проверяет один файл описания объекта (корень `MetaDataObject`) по XSD его формата из namespace-forest.
При несоответствии печатает `файл:строка:столбец: сообщение` и завершается с кодом 1. Файлы с другим
корнем - содержимое `Ext` (права, справка, формы, макеты и т.п.), `ConfigDumpInfo.xml`, `.mdo` проекта
1С:EDT - отклоняются с кодом 2: поправки схем, описанные ниже, сделаны только для описаний объектов.
Для прав и справки схем в наборе нет, а схемы форм, макетов и предопределённых данных без поправок
с выводом платформы не сходятся.

Формат файла (`MetaDataObject/@version`) должен совпадать с `-v`, иначе код 2: схема более нового формата
допускает версии всех прежних и пропустила бы в файле старого формата то, чего этот формат не знает
(например, объект вида, которого у его платформы нет).

Если схема формата не собирается (в корне namespace-forest не хватает файла или он испорчен), `validate`
печатает файл XSD и место ошибки в нём и завершается с кодом 2: проверяемый файл тут ни при чём.

Схемы namespace-forest - выгрузка XDTO самой платформы (`ФабрикаXDTO.ЭкспортСхемыXML`). Они описывают модель
XDTO, а не файлы выгрузки, и как есть не пропускают ни одного файла объекта. Поэтому перед проверкой схема
правится в памяти, файлы схем не меняются:

| В XDTO | Платформа пишет | При проверке |
| --- | --- | --- |
| свойства объекта (`*Properties`) - последовательность, почти все обязательны | без значений по умолчанию (`ObjectBelonging`), без модулей, справки, прав и прочего из отдельных файлов; у заимствованного объекта - почти ничего; порядок свойств свой | любое свойство может отсутствовать, порядок любой |
| `ConfigurationProperties`, `CommonModuleProperties`, `StandardAttributeDescription`, `Picture` - ровно одно свойство (`xs:choice`) | все свойства подряд | как свойства объекта |
| `ConfigurationChildObjects`: `Bot`, `WebSocketClient`, `PaletteColor` в конце | `WebSocketClient` после `WSReference`, `Bot` и `PaletteColor` после `DefinedType` | порядок платформы |
| `Configuration/@formatVersion` обязателен | не пишет | необязателен |
| `MinValue`, `MaxValue`, `FillValue` без `nillable` | «Неопределено» как `xsi:nil="true"` | `xsi:nil` допустим у элементов без типа |
| `InternalInfo`: `GeneratedType` перед `ContainedObject` | у внешних обработок и отчётов наоборот | вперемешку |
| `LinkByType`: обязателен `DataPath` | `<LinkByType/>` | `DataPath` необязателен |
| `ValueList`: ровно один `Item` | пустой список или несколько элементов | сколько угодно |
| `MDObjectRef`: шаблон `([A-Za-z0-9_])*` | `Role.ПолныеПрава` | строка |
| `DataPath` | `xsi:type="xs:string"` в связях параметров выбора | строка |
| `ExtendedProperty` ни от чего не выводится | расширяемое свойство заимствованного объекта: `<Type xsi:type="xr:ExtendedProperty">` | допустимо у свойств типа `TypeDescription` |
| `CompatibilityMode`: `DontUse` и режимы до `Version8_3_12` | и режимы новее (`Version8_3_27`), и номер своей версии (`Version8_5_1`). Режима совместимости 8.5 нет, потому что нет ничего, что поддерживает только 8.5, - это норма | `DontUse` или `Version` с номером через `_` |
| `MobileApplicationFunctionalities` | ещё `SpeechToText` с 2.17, `TextToSpeech` с 2.18 | допустимы с того же формата |
| `app:permission` (2.10): обязателен `description` | без `description` | необязателен |

Ошибкой остаются неизвестный элемент, повтор свойства, неверное значение перечисления или простого типа,
элемент не на своём месте (свойство вне `Properties` и т.п.), нарушение порядка в `ChildObjects` и
`InternalInfo`. Не проверяются полнота свойств и их порядок внутри `Properties`: у XDTO он свой.

Проходят все файлы объектов выгрузки ssl31 (конфигурация, расширения, внешние обработки и отчёты,
формат 2.20) и все эталоны samples-1c-platform форматов 2.10-2.21 (`XmlValidatorPlatformOutputTest`).
Отрицательные случаи - намеренно испорченные копии тех же файлов (`XmlValidatorTest`).
