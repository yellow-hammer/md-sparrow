# Свойства объектов метаданных (cf-md-object)

Контракт CLI-команд чтения и записи свойств объектов метаданных. Данные читаются и записываются только через JAXB: вызывающая программа получает и отдаёт DTO, XML на её стороне не правится.

## Команды CLI

| Команда                                      | Назначение           |
|----------------------------------------------|----------------------|
| `cf-md-object-get <путь.xml> -v V2_10…V2_21` | stdout: один JSON    |
| `cf-md-object-set <путь.xml> <json> -v …`    | запись из файла JSON |
| `cf-md-object-enums -v V2_10…V2_21`          | stdout: JSON допустимых значений перечислимых свойств |

### CRUD дочерних узлов объекта

| Команда                                               | Назначение                |
|-------------------------------------------------------|---------------------------|
| `cf-md-attribute-add/rename/delete/duplicate`         | Реквизиты объекта         |
| `cf-md-command-add/rename/delete`                     | Команды объекта           |
| `cf-md-tabular-section-add/rename/delete/duplicate`   | Табличные части объекта   |
| `cf-md-tabular-attribute-add/rename/delete/duplicate` | Реквизиты табличной части |

Добавление узла, которого у вида владельца нет по схеме формата (`<Вид>ChildObjects` модели версии), отклоняется: «У вида Catalog нет подчинённых Dimension». Платформа такой узел при загрузке молча выбрасывает.

К объекту, заимствованному в расширении, свои реквизиты, табличные части, измерения, ресурсы и признаки учёта добавляются только у справочника, документа, перечисления, обработки, отчёта, плана обмена, бизнес-процесса и задачи. У заимствованных регистров, последовательности, плана счетов, плана видов характеристик и плана видов расчёта такое добавление и копия узла отклоняются: расширение с ними платформа не применяет («Добавление дочерних объектов этого типа к заимствованным в расширениях недопустимо в режиме совместимости 8.5.1 и ниже», `ibcmd infobase config check --extension` на 8.3.27 и 8.5.1 в режимах совместимости 8.3.24, 8.3.27 и 8.5.1). Команды добавляются к заимствованному объекту любого вида.

Имя нового узла, копии и новое имя при переименовании сверяются так, как имена сравнивает платформа (`ibcmd infobase config import` на 8.3.23, 8.3.24, 8.3.27 и 8.5.1 отвечает одинаково); иначе выгрузку она не загружает целиком:

- без учёта регистра: реквизит «ЦЕНА» рядом с «Цена» отклоняется («Реквизит уже существует: Цена»; платформа - «Дублирование имени объекта метаданных»). Сменить регистр имени самого узла можно, а сам узел правки ищется по имени, как оно написано в файле;
- поля данных - реквизиты, табличные части, измерения, ресурсы, признаки учёта и реквизиты адресации - делят одно пространство имён: реквизит с именем табличной части, ресурс с именем измерения, признак учёта с именем реквизита отклоняются («Имя Товары уже занято: табличная часть Товары»; платформа - «Задано одинаковое имя для реквизита и табличной части»). Команды, формы, макеты, значения перечисления и признаки учёта субконто называются независимо от полей и друг от друга: пары вроде реквизита и команды «Цена» платформа загружает, есть они и в ssl31. Реквизит табличной части сверяется только с реквизитами своей табличной части;
- полю данных нельзя дать имя стандартного реквизита, стандартной табличной части или свойства объекта на любом из языков («Код», «Code», «Наименование», «ЭтотОбъект», «Движения» документа, «Период» регистра), реквизиту табличной части - «НомерСтроки» и, у ссылочного объекта, «Ссылка» (платформа - «Недопустимое имя реквизита»). Список снят с платформы и лежит в `ChildNodeNames`: от настроек объекта он не зависит, а «Предопределенный» справочника, «Порядок» плана счетов, значения перечисления, команды и признаки учёта субконто платформа принимает;
- у внешних отчёта и обработки платформа (`ibcmd infobase config import --out`) отвергает только одноимённые узлы одного вида и реквизит табличной части «НомерСтроки»: поля разных видов с одним именем и имена вроде «ЭтотОбъект» она собирает в файл без ошибок.

Новый узел (реквизит, табличная часть и её реквизит, команда, значение перечисления, измерение, ресурс, признаки учёта) пишется так, как его пишет конфигуратор: все свойства со значениями по умолчанию платформы, тип реквизита, измерения и ресурса - строка 10, у признаков учёта - булево, у команды группа `FormCommandBarImportant`. Узел берётся из эталона платформы для своего вида владельца и формата, подпись - на языке конфигурации. Место в `ChildObjects` - как у платформы: виды узлов идут в порядке схемы, новый узел - последним среди узлов своего вида. UUID нового узла и копии детерминированы: повтор той же правки над тем же файлом даёт те же байты. Как получены эталоны - [scaffold-golden.md](scaffold-golden.md#дочерние-узлы).

Структура объекта (секции, ТЧ, вложенные узлы) — `cf-md-object-structure-get`. Кроме состава она отдаёт синонимы, которыми платформа подписывает элементы формы: `standardAttributeSynonyms` - синонимы стандартных реквизитов (`Code` у справочника валют это «Цифровой код»), `commandSynonyms` - синонимы команд объекта. У табличных частей свои `standardAttributes` и `standardAttributeSynonyms`. Стандартные табличные части плана счетов и плана видов расчёта лежат в `standardTabularSections`: имя, подпись в `synonym` и подписи их стандартных реквизитов.

Синоним стандартного реквизита файл хранит только переопределённым, поэтому пустой заменяется подписью платформы: `LineNumber` это «N». Модель формата такие подписи не объявляет, словарь ведётся в `StandardAttributeLabels` и наполняется сверенным с конфигуратором.

`childSynonyms` - синонимы полей данных, которые в списках лежат одними именами: измерения, ресурсы, признаки учёта, колонки. По ним подписываются колонки динамического списка: его поля идут по именам основной таблицы, а её отдаёт `mainTable` у реквизита формы в `cf-form-content-get`.

### Таблицы языка запросов (`cf-md-query-tables`)

`cf-md-query-tables` (канал `read-json`) отдаёт таблицы, которые объект даёт в языке запросов: основную, табличные части, стандартные табличные части и виртуальные таблицы регистров, таблицу критерия отбора и таблицы последовательности — с полями, их типами и параметрами. Им пользуются конструктор запроса редактора СКД (дерево «База данных») и подсказка полей «через точку». `cf-md-object-structure-get` для этого не годится: он отдаёт стандартные реквизиты английскими именами и тем составом, что записан в файле.

Вход: `objectXml` — файл объекта (`<Вид>/<Имя>.xml` выгрузки или `<Вид>/<Имя>/<Имя>.mdo` проекта 1С:EDT), `schemaVersion` (`V2_xx`; у `.mdo` не нужен), `lang` — `ru` (по умолчанию) или `en`. Ответ у выгрузки и у проекта EDT одинаков.

```json
{"object": "РегистрНакопления.ОстаткиТоваров", "kind": "accumulationRegister",
 "tables": [
  {"name": "РегистрНакопления.ОстаткиТоваров", "kind": "main", "synonym": "Остатки товаров", "params": [],
   "fields": [{"name": "Период", "nameEn": "Period", "kind": "standard",
     "type": {"types": ["xs:dateTime"], "typeSets": [], "dateQualifiers": {"dateFractions": "DATE_TIME"}},
     "synonym": "Период"},
    {"name": "Регистратор", "nameEn": "Recorder", "kind": "standard", "type": null, "synonym": "Регистратор"}]},
  {"name": "РегистрНакопления.ОстаткиТоваров.Остатки", "kind": "virtual", "synonym": "",
   "params": [{"name": "Период", "kind": "period"}, {"name": "Условие", "kind": "condition"}],
   "fields": [{"name": "КоличествоОстаток", "nameEn": "КоличествоBalance", "kind": "resource",
     "type": {"types": ["xs:decimal"], "typeSets": []}, "synonym": "", "source": "Количество"}]}]}
```

- `object` и `tables[].name` — полные имена таблиц, как их пишут после `ИЗ`; имена видов, таблиц, стандартных реквизитов, параметров и суффиксов — на языке `lang` (словарь `query-names.json` рядом с `standard-labels.json`), свои имена объекта (реквизиты, измерения, ТЧ) не переводятся; `synonym` — всегда на языке конфигурации (у стандартных реквизитов — переопределённый в файле синоним либо подпись платформы, у ВерсияДанных, Представление, МоментВремени и полей виртуальных таблиц — пусто).
- `tables[].kind`: `main` | `tabularSection` | `standardTabularSection` | `virtual`. У таблицы всегда есть `params` (пусто, кроме виртуальных таблиц регистров и задачи и таблицы критерия отбора) и `fields`. Таблица критерия отбора — единственная `main` с непустыми `params`: другой таблицы у критерия нет, а основной она числится, чтобы имя объекта без хвоста находило её, как у прочих видов. `Границы` последовательности — `virtual` с пустыми `params`.
- `params[]` — параметры таблицы по позициям: `name`, `kind` (`period`, `periodStart`, `periodEnd`, `periodicity`, `method`, `condition`, `account`, `extDimensions`, `corAccount`, `corExtDimensions`, `accountDr`, `extDimensionsDr`, `accountCr`, `extDimensionsCr`, `order`, `top`, `performer`, `value`); у `periodicity` и `method` ещё `values` — значения для выбора: у `periodicity` в порядке списка конструктора Период, Запись, Регистратор, [УточнениеПериода], Секунда, Минута, Час, День, Неделя, Декада, Месяц, Квартал, Полугодие, Год, Авто; `УточнениеПериода` (`PeriodAdjustment`) — только у `Обороты`, `ОстаткиИОбороты` и `ОборотыДтКт` регистра бухгалтерии с «Длиной уточнения периода» (`PeriodAdjustmentLength`) больше 0; у `method` — Движения, ДвиженияИГраницыПериода. У параметра `value` (значение критерия отбора, `Значение`/`Value`) ещё `required: true` и `type` — свойство «Тип» критерия формой `MdTypeDescriptionDto` или `null`, если тип не задан; у остальных параметров этих ключей нет.
- `fields[]`: `name`, `nameEn`, `kind` (`standard`, `attribute`, `dimension`, `resource`, `addressingAttribute`, `accountingFlag`, `extDimensionAccountingFlag`, `column`, `period`, `separator`, `commonAttribute`), `type`, `synonym`; у полей ресурсов виртуальных таблиц, пар Дт/Кт и корреспондирующих полей `<Имя>Кор` — `source` (имя измерения или ресурса объекта); у измерений и ресурсов регистра бухгалтерии — `balance` (признак «Балансовый» читается из XML, в `cf-md-object-get` его нет). Поля общих реквизитов: `kind` — `separator` у разделителя («Разделение данных» — «Разделять») и `commonAttribute` у прочих, `name` = `nameEn` = имя реквизита, `type` и `synonym` — реквизита, `source` — `CommonAttribute.<Имя>`, у разделителя ещё `separatedDataUse` — «Использование разделяемых данных» константой модели (`INDEPENDENTLY` | `INDEPENDENTLY_AND_SIMULTANEOUSLY`, как в `cf-md-object-get`); подробности — ниже, «Общие реквизиты».
- `type` — форма `MdTypeDescriptionDto` (как у `cf-md-object-get`) либо `null`, и ключ есть всегда: у своих узлов объекта — тип из описания; у стандартных реквизитов — по правилам вида: `Ссылка` и `Родитель` — ссылка на сам объект, `Ссылка` табличной части — ссылка на владельца, `Код` и `Номер` — строка длины объекта (с её `AllowedLength`) либо неотрицательное целое стольких же цифр, `Наименование` — строка длины объекта, `Владелец` — ссылки по списку владельцев, `Ссылка` журнала — ссылки его документов, счёт — ссылка на план счетов регистра, субконто — `cfg:Characteristic.<ПВХ>` плана счетов, вид субконто — ссылка на этот ПВХ, булевы признаки — `xs:boolean`, даты и периоды — `xs:dateTime` (дата и время). Где тип зависит от других объектов или от перечислений платформы, `type: null`: `Регистратор` (кроме последовательности: у неё это ссылки на её документы), `ВидДвижения`, `МоментВремени`, `Тип` и `Номер` журнала, `Вид` плана счетов, `ТипЗначения`, `ВедущаяЗадача`, `БизнесПроцесс` и `ТочкаМаршрута` задачи, графы журнала. `ВерсияДанных`, `Представление`, `ИмяПредопределенныхДанных`, `Порядок` плана счетов — строка без квалификаторов, `НомерСтроки`, `Порядок` перечисления, номера сообщений плана обмена — число без квалификаторов.
- `typeCompositions[]` — составы наборов типов, встреченных в полях любой таблицы ответа (основной, ТЧ, стандартных ТЧ, виртуальных, субконто, значения константы, измерений последовательности) и в типе параметра критерия отбора: по одной записи `{source, types, typeSets}` на набор, в порядке первого вхождения при обходе таблиц, а в таблице — сначала параметров, потом полей (в порядке ключей ответа). `source` — `cfg:DefinedType.<Имя>` (определяемый тип) или `cfg:Characteristic.<ПВХ>` (характеристика: тип значения плана видов характеристик — так типизированы субконто и реквизиты-характеристики). Сам `type` поля называет набор, а потребитель, которому нужно разыменовать поле «через точку» или предложить связь, берёт ссылки из записи. Отдельный ключ, а не состав в каждом `type`: определяемый тип из двух десятков ссылок стоит в десятках полей и в их копиях в виртуальных таблицах, и ответ вырос бы в разы. Подробности ниже.
- `notes[]` — есть, только когда ответ неполон: например, план счетов регистра бухгалтерии не найден рядом в выгрузке — тогда субконто не перечисляются (их число задаёт план счетов).

Порядок ключей ответа: `object`, `kind`, `tables`, `typeCompositions` (если есть), `notes` (если есть).

Составы (`typeCompositions`). Читает их общий класс составов (`TypeCompositions`, тот же, что у `definedTypes[].composition` словаря `cf-dcs-type-dictionary`, см. `docs/cf-dcs.md`): определяемый тип — элемент `Type` свойств `DefinedTypes/<Имя>.xml` выгрузки или корневой `type` файла `DefinedTypes/<Имя>/<Имя>.mdo` проекта EDT; характеристика — тип значения `ChartsOfCharacteristicTypes/<Имя>.xml` (`.mdo`). Запись — как у типов полей этого ответа: `xs:decimal`, `v8:ValueStorage`, `cfg:CatalogRef.Валюты`, наборы вида (`cfg:CatalogRef`) и «любая ссылка» (`cfg:AnyIBRef`, и у проекта EDT) остаются в `typeSets`. Вложенный определяемый тип или характеристика в составе подставляется своим составом; набор, замыкающий цикл, и набор без описания остаются в `typeSets`. Квалификаторов в записи нет — они у словаря. Ключа нет, если наборов в полях нет, файл объекта лежит вне выгрузки (составы взять неоткуда) или ни одно описание не найдено; запись ненайденного набора просто не появляется, отказа нет. Пример для `Справочник.Пользователи` ssl31 (запись характеристики `ДополнительныеРеквизитыИСведения` из ТЧ опущена):

```json
"typeCompositions": [
  {"source": "cfg:DefinedType.Подразделение", "types": ["cfg:CatalogRef._ДемоПодразделения"], "typeSets": []},
  {"source": "cfg:DefinedType.ФизическоеЛицо", "types": ["cfg:CatalogRef._ДемоФизическиеЛица"], "typeSets": []}]
```

Составы определяемых типов совпадают с `definedTypes[].composition` словаря, составы характеристик — с типом значения плана видов характеристик из `cf-md-object-get`; у проекта EDT записи те же. Язык `lang` на составы не влияет.

Состав стандартных реквизитов выводится из вида и свойств объекта (`cf-md-object-get`), а не из XML: файл перечисляет стандартные реквизиты с настройками, даже когда их у объекта нет (у неиерархического справочника `Валюты` записаны `Parent` и `IsFolder`), и не перечисляет всегда присутствующие (`ВерсияДанных`, `Представление`).

Общие реквизиты. Реквизит применён к объекту, если в его составе (`Content`) у объекта стоит «Использовать» (`Use`); «Не использовать» (`DontUse`) — не применён; «Авто» или объекта в составе нет — применён, только когда «Автоиспользование» (`AutoUse`) — «Использовать». Условное разделение на состав полей не влияет, режим «Использование разделяемых данных» тоже: разделитель отдаётся в любом режиме вместе с `separatedDataUse`, а что показывать, решает потребитель. Реквизиты читаются из каталога `CommonAttributes` той же конфигурации, что и объект (`<Имя>.xml` выгрузки, `<Имя>/<Имя>.mdo` проекта EDT — у EDT умолчания модели: без `autoUse` — «Использовать», без `use` элемента состава — «Авто»); файл объекта вне выгрузки или выгрузка без каталога — полей нет и ошибки нет; нечитаемый файл реквизита пропускается с записью в `notes`. Реквизит, заимствованный расширением (`ObjectBelonging` — `Adopted`), не перечисляется ни у выгрузки, ни у EDT: его тип, разделение и автоиспользование — в основной конфигурации, а файл расширения их не несёт (у EDT подставились бы умолчания модели — разделитель с автоиспользованием); в `notes` — «Общий реквизит <Имя> заимствован расширением: его свойства — в основной конфигурации, поля не перечислены.». Прочитанные реквизиты кэшируются по пути, размеру и времени изменения файла.

| Остатки, Обороты, ОстаткиИОбороты регистра накопления; Остатки, Обороты, ОстаткиИОбороты, ОборотыДтКт регистра бухгалтерии | только разделители | сразу за измерениями (в `Обороты` — за `<Имя>Кор`) |

Не делаются: таблица Константы (все константы одной таблицей), внешние источники данных (отказ, как у прочих неописанных видов), таблицы изменений, РегистрБухгалтерии.Субконто, ДанныеГрафика, базовые таблицы и перерасчёты регистра расчёта, ДатаОбмена плана обмена, ТЧ как поле основной таблицы (`Документ.Товары` через точку); у прочих видов объектов (отчёт, общий модуль…) — отказ «Таблиц языка запросов у объекта вида … нет». Регистратор регистров и бизнес-процесс задачи без типа: их тип — обратная ссылка по движениям документов и по бизнес-процессам конфигурации.

### Допустимые значения перечислимых свойств

`cf-md-object-enums` отдаёт словарь `блок.свойство` → константы модели, например `{"chartOfCharacteristicTypes.codeSeries":["WHOLE_CHARACTERISTIC_KIND","WITHIN_SUBORDINATION"]}`. Набор снимается с модели запрошенной версии формата, поэтому вызывающей программе не нужна своя копия списка: при записи значение вне этого набора отклоняется с перечислением допустимых.

### Права ролей на объект

`cf-object-rights-get` (канал `read-json`) отдаёт права всех ролей на объект из `objectXml`: права его вида в порядке платформы (`rights`), права, которые каждое из них тянет за собой (`requires`), и у каждой роли действующие права с учётом «Устанавливать права для новых объектов», ограничения доступа и записанные права подчинённых. `editable` ложно у вида, прав на который в ролях нет.

`cf-object-rights-set` (канал `apply-mutation`) принимает `payloadJson` вида `{"edits":[{"role":"Кладовщик","right":"Read","value":true}]}`. Выданное право тянет нужные ему, снятое снимает зависящие; значение, равное умолчанию роли, из файла уходит, а право с ограничениями доступа остаётся с ними при любом значении. Роль на поддержке поставщика без возможности изменения не правится: в чтении у неё `readonlyReason`, запись отказывает с именем роли и не меняет файлы ни одной роли.

Обе операции работают с выгрузкой конфигуратора (`Roles/<Роль>/Ext/Rights.xml`) и с проектом 1С:EDT (`Roles/<Роль>/Rights.rights`, поддержка из `Configuration/Configuration.distr`).

## Создание объектов (`add-md-object`)

`add-md-object` создаёт объект верхнего уровня любого вида, кроме языка и устаревшего интерфейса: в выгрузке конфигуратора (путь к `Configuration.xml`, CLI и канал `apply-mutation`) и в проекте 1С:EDT (путь к `Configuration/Configuration.mdo`, канал `apply-mutation`). Вид задаёт `--type` (`type` в канале): имя константы из таблицы, регистр и разделители не важны, годится и имя элемента состава (`information-register`, `InformationRegister`). С `--auto-name` имя подбирается как у конфигуратора: префикс вида и первый свободный номер («РегистрСведений1»). Явно заданное занятое имя получает отказ «Справочник «Товары» уже есть.», и ничего не пишется, в обоих форматах: имя занято, если оно есть в составе конфигурации или на диске уже лежит описание либо каталог объекта. Другое имя вместо заданного операция не берёт: следующая правка, например в пакете `apply-mutation`, обращается к объекту по заданному имени. Синоним задаётся только справочнику (`--synonym-ru`, `--synonym-empty`), у остальных видов он пустой, как в эталоне.

**Формат.** Вид, которого в формате ещё нет, не создаётся, выгрузка и проект не меняются: «вид PaletteColor появился в формате 2.21 (платформа 8.5.1), в формате 2.20 его нет». Столбец «С формата» - по модели формата (`FormatProjection.hasObjectKind`), он же совпадает с тем, что выгружает платформа. Формат выгрузки - `-v` (`schemaVersion`), у проекта EDT - формат линейки его платформы (`Runtime-Version` в `DT-INF/PROJECT.PMF`, `SchemaVersion.ofPlatform`): в проекте 8.3.27 нет цвета палитры, в проекте 8.3.17 - бота и клиента WebSocket. Проект без манифеста принимает любой вид.

**Место в составе.** Ссылка в `Configuration.xml` встаёт в блок своего вида в порядке платформы (см. [cf-layout.md](cf-layout.md#добавление-объекта-add-md-object)), в `Configuration.mdo` - в порядке признаков класса `Configuration` схемы EDT.

**Общая форма.** Корень `Ext/Form.xml` объявляет пространство схемы компоновки (`xmlns:dcssch`) по режиму совместимости конфигурации, как платформа: с `Version8_3_19` объявляет, в более старых режимах и в `DontUse` - нет. В расширении действует его собственный режим `ConfigurationExtensionCompatibilityMode`, а не режим основной конфигурации.

**Проверка конфигурации платформой.** Голые объекты 14 видов, как и новые объекты конфигуратора, обычную загрузку с проверкой не проходят - платформа требует заполнить свойства или состав. Загрузка без проверки (`ibcmd infobase config import files --no-check`) принимает все виды. Чем дополнить объект и есть ли для этого операция md-sparrow:

который читается и пишется целиком, гранулярно по изменённым элементам.

Для `catalog`, `document`, `exchangePlan`:

- `attributes[]`, `tabularSections[]`: элементы `{ "name", "synonymRu", "comment", "type" }` плюс свойства палитры: `toolTipRu`, `fillChecking`, `indexing`, `fullTextSearch`, `dataHistory`, `use`, `quickChoice`, `createOnInput`, `choiceHistoryOnInput`, `choiceForm`, `choiceParameters`, `choiceParameterLinks`. Набор свойств зависит от вида узла и версии формата: чего в схеме нет, приходит пустым и при записи не трогается. Допустимые значения перечислений отдаёт `cf-md-object-enums` под ключами вида `attribute.indexing`. Имя **не меняется** через `cf-md-object-set`; при сохранении число и порядок элементов должны совпадать с XML.

**Значение заполнения при смене типа.** У узла с `FillValue` (реквизит, реквизит адресации, измерение и ресурс регистра сведений, признак учёта) смена `type` через `cf-md-object-set` ставит то значение заполнения, которое выгрузит платформа. Значение, тип которого есть в новом типе узла, и `xsi:nil` остаются байт в байт. Значение типа `xs:string`, `xs:decimal`, `xs:boolean` или `xs:dateTime`, которого в новом типе нет, заменяется пустым: `<FillValue xsi:type="xs:string"/>`, если новый тип — только строка, иначе `<FillValue xsi:nil="true"/>`.

- Так значение хранит платформа: загрузка (ibcmd 8.3.27, формат 2.20) заменяет неподходящее значение заполнения на `xsi:nil`, а пустую строку у строки и составного типа со строкой оставляет — она к ним подходит. Пустая строка — и форма, в которой платформа создаёт строковый узел.
- Значение конфигурации (`xr:DesignTimeRef`) не трогается: в ssl31 есть значение одного перечисления при типе другого перечисления (`ВопросыДляАнкетирования`, `ВидФлажка`), и платформа его хранит. При определяемом типе или характеристике в новом типе значение тоже не трогается: их состав лежит у другого объекта.
- Сверх типа значение не сверяется: число вне новой разрядности и строка длиннее новой длины остаются как есть.
- В проекте EDT правило то же (и у реквизитов табличных частей): вместо nil — `core:UndefinedValue`, вместо пустой строки — самозакрытый `core:StringValue`, как у нового реквизита.
- Эхо файла не меняет: запись того же типа (или того же с другими квалификаторами) подходящее значение не трогает.

Новый узел (`cf-md-attribute-add` и другие операции добавления) пишется по эталону платформы: строка с пустым значением заполнения, у признаков учёта — булево с nil.

Для `subsystem`:

- `nestedSubsystems[]`: строки — вложенные подсистемы в `ChildObjects`
- `contentRefs[]`: состав подсистемы из `Properties/Content`, читается и пишется через `cf-md-object-set`

## Ограничения текущего этапа

- Для всех перечисленных `kind` поддержаны базовые поля `internalName/synonymRu/comment` с гранулярной записью.
- Типизированный блок свойств есть у видов из строк «полная». Остальные виды отдают одиночные свойства словарём `scalars` (имя свойства выгрузки и значение) с описаниями `scalarMeta` (тип и допустимые значения). Внешние свойства, которые лежат своими файлами (модуль, справка, картинка, командный интерфейс, дополнительные индексы), в словарь не попадают. Принадлежность объекта (`ObjectBelonging`) словарём не правится.
- Для `subsystem` дополнительно поддержаны `nestedSubsystems` и `contentRefs`. Тем же полем `contentRefs` приходят состав функциональной опции, использование её параметра и состав критерия отбора: у критерия ссылки только снимаются, дерево кандидатов не строится. Состав общего реквизита - `contentMembers[]` (`ref`, `mode`, `conditionalSeparation`), у последовательности - `documents[]` и `registerRecords[]`.
- В проекте 1С:EDT списки ссылок читаются и пишутся так же, как в выгрузке: состав, вложенные подсистемы, использование параметра, документы и движения, владельцы, ввод на основании, ввод по строке, поля блокировки, основные роли конфигурации. Правка списка заменяет его элементы, остальной файл не меняется. Использование `AUTO` в составе общего реквизита 1С:EDT не пишет.
- Словарь `scalars` в проекте 1С:EDT тот же, что у выгрузки: ключ - имя свойства выгрузки, значение лежит в одноимённом свойстве схемы EDT со строчной буквы. Значение по умолчанию 1С:EDT в файл не пишет, словарь берёт его из схемы; свойства, которые и выгрузка пишет только заданными (принадлежность, использование в режиме совместимости интерфейса), без записи пусты. Пустое значение снимает свойство из файла.
- Правка списка или свойства, которого у вида нет, получает отказ, файл не меняется.
- Параметры выбора (`choiceParameters`) читаются текстом и не пишутся: значение платформа хранит типизированным, строкой его не восстановить. Связи параметров выбора (`choiceParameterLinks`: `name`, `dataPath`, `mode`) читаются и пишутся целиком, число и порядок связей при записи должны совпадать с XML.
- Состав плана обмена лежит отдельным файлом `<План>/Ext/Content.xml` и правится операцией `cf-md-exchange-plan-content-set`.
