# Схема компоновки данных (cf-dcs)

Контракт CLI-операций чтения и правки схемы компоновки данных: макет вида «Схема компоновки данных» у отчёта, обработки или общего макета. В выгрузке конфигуратора это `Templates/<Макет>/Ext/Template.xml`, в проекте 1С:EDT — `Templates/<Макет>/Template.dcs`; формат файла один, операции работают с обоими путями одинаково.

Чтение идёт JAXB-моделью схемы (пространство `v8.1c.ru/8.1/data-composition-system/schema`); варианты настроек читаются текстовым слоем файла — модели не хватает дословных `xsi:type` значений. Запись — точечная правка текста по якорям строк, не пересериализация:

- нетронутые части файла совпадают байт в байт: правка остаётся одной непрерывной зоной;
- BOM, переводы строк (CRLF/LF), табы и отсутствие перевода строки в конце сохраняются;
- новый или заменяемый подэлемент встаёт строго на место по `xs:sequence` XSD формата (`v8.1c.ru-8.1-data-composition-system-schema.xsd`);
- текст экранируется, как у платформы: только `&`, `<` и `>`;
- многострочный текст пишется дословно, переводы строк приводятся к переводу строки файла (см. [«Многострочный текст»](#многострочный-текст));
- заголовки пишутся `v8:LocalStringType` с языком конфигурации (см. `ConfigurationLanguage`);
- перед записью правленый текст перечитывается моделью: битый файл не пишется;
- `userSettingID` вариантов настроек и прочие UUID не трогаются;
- отказ ничего не меняет: канал отвечает кодом 2 и текстом причины в stderr.

Все операции идут каналами `read-json` и `apply-mutation` (см. [write-session.md](write-session.md): проверка без записи, пакет операций). Общие поля параметров: `objectXml` — путь к файлу схемы, `schemaVersion` — `V2_10`…`V2_21` (номер формата `"2.20"` вместо имени: отказ с подсказкой).

## Чтение

| Операция (`read-json`) | Назначение |
|---|---|
| `cf-dcs-info` | stdout: JSON со структурой схемы |
| `cf-dcs-settings-info` | stdout: JSON вариантов настроек, см. [«Варианты настроек»](#варианты-настроек) |
| `cf-dcs-validate` | stdout: `{"valid":true,"dataSetCount":N}` либо `{"valid":false,"error":"…"}`; с `strict: true` — `{"ok":…,"errors":[…],"warnings":[…]}`, см. [«Строгая проверка схемы»](#строгая-проверка-схемы) |
| `cf-dcs-type-dictionary` | stdout: JSON словаря окна «Тип значения», см. [«Типы значений»](#типы-значений) |
| `cf-md-query-tables` | stdout: таблицы языка запросов объекта метаданных для конструктора запроса, см. [cf-md-object.md](cf-md-object.md#таблицы-языка-запросов-cf-md-query-tables) |

`cf-dcs-info` отдаёт блоки `dataSets`, `calculatedFields`, `totalFields`, `parameters`, `dataSources`, `dataSetLinks`, `nestedSchemas`, `settingsVariants` и последним — необязательный `typeCompositions`. Необязательные поля в JSON присутствуют, только когда они записаны в файл; локализованные строки отдаются на языке конфигурации.

- `dataSets[]`: `name`, `type` (`query` | `object` | `union`), `dataSource`, `objectName`, `query`, `autoFillFields` (у запроса; отсутствие элемента в файле значит `true`), `fields[]`; у объединения — `items[]` с вложенными наборами, рекурсивно.
- `fields[]` набора: `dataPath`, `kind` (`field` | `folder` | `nested`), `field`, `title`, `titleLangs` (все языки заголовка: код языка → текст), `useRestriction` и `attributeUseRestriction` (`{field, condition, group, order}` — четыре флага; невзведённые платформа в файл не пишет), `role`, `valueTypePresentation` (тип значения строкой, только чтение), `hasAppearance` и `hasInputParameters` (признаки, что секция в файле есть).
- `role` поля: `periodNumber`, `periodType` (`Main` | `Specify` | `Additional`), `dimension`, `parentDimension`, `account`, `accountTypeExpression`, `balance`, `balanceGroupName`, `balanceType` и `accountingBalanceType` (`None` | `OpeningBalance` | `ClosingBalance`), `accountField`, `ignoreNullValues`, `required`, `dimensionAttribute`, `isMain` — только записанные в файл значения.
- `calculatedFields[]`: `name` (путь к данным), `value` (выражение), `title`, `useRestriction`, `hasAppearance`.
- `totalFields[]` (ресурсы): `name` (путь к данным), `value` (выражение), `groups[]` (имена группировок; без них итог считается по всем).
- `parameters[]`: `name`, `title`, `type` (состав типа строкой), `value` (лексическое значение), `expression`, `useRestriction`, `use` (`Always`; `Auto` платформа не пишет — это умолчание), `availableAsField`, `denyIncompleteValues`, `valueListAllowed`, `valuePresentation` (значение строкой для показа, только чтение).
- `dataSources[]`: `name`, `type` (тип источника, `dataSourceType` файла), `connectionString`.
- `dataSetLinks[]`: `source`, `destination`, `sourceExpression`, `destinationExpression`, `parameter`, `parameterListAllowed`, `linkConditionExpression`, `startExpression`, `required` (только если записан в файле: платформа его не хранит, см. [«Связи наборов»](#связи-наборов)).
- `nestedSchemas[]`: `name` и `value` (заголовок) — только чтение. `settingsVariants[]`: `name` и `value` (представление) — обзорный список; состав варианта читается и правится операциями раздела [«Варианты настроек»](#варианты-настроек).
- `valueType` — структурный тип значения у `fields[]` наборов (включая вложенные наборы объединений), `calculatedFields[]` и `parameters[]`, см. [«Типы значений»](#типы-значений). У параметров ещё `hasAvailableValues` и `hasInputParameters`: признаки, что в файле есть доступные значения и параметры выбора (смена типа может их рассогласовать).
- `valueTyped` — значение параметра в форме значений настроек, её же принимает `value` у `cf-dcs-set-parameter`, см. [«Значение параметра: valueTyped»](#значение-параметра-valuetyped).
- `typeCompositions[]` — составы определяемых типов и характеристик из `valueType` схемы, по записи `{source, name?, types, typeSets}` на тип, см. [«Составы определяемых типов и характеристик: typeCompositions»](#составы-определяемых-типов-и-характеристик-typecompositions).

Пример (сокращён):

```json
{

    {
      "name": "ОсновнойЗапрос",
      "type": "query",
      "dataSource": "ИсточникДанных1",
      "query": "ВЫБРАТЬ …",
      "autoFillFields": true,
      "fields": [
        {
          "dataPath": "Сумма",
          "kind": "field",
          "field": "Сумма",
          "title": "Сумма документа",
          "titleLangs": {"ru": "Сумма документа"},
          "useRestriction": {"field": false, "condition": false, "group": true, "order": false},
          "role": {"dimension": true, "ignoreNullValues": true}
        }

    }
  ],
  "calculatedFields": [{"name": "Наценка", "value": "Сумма * 0.1", "title": "Наценка"}],
```

### Типы значений

`valueType` — форма `MdTypeDescriptionDto` плюс признаки редактора:

```json
{"types": ["xs:string"], "typeSets": ["cfg:AnyIBRef"], "typeIds": [],
 "stringQualifiers": {"length": "150", "allowedLength": "VARIABLE"},
 "editable": true}
```

- `types[]` (`v8:Type`), `typeSets[]` (`v8:TypeSet`), `typeIds[]` (`v8:TypeId`) — всегда массивы, в порядке файла. Префикс нормализован по пространству имён: в файле у ссылочного типа свой префикс на каждом элементе (`d4p1:`, `d5p1:` — по глубине), в ответе всегда `cfg:`; `xs:` и `v8:` — как в файле.
- `definedTypes[]` — имена определяемых типов по порядку `typeIds`. В схеме определяемый тип записан только UUID, имя ищется по `DefinedTypes` выгрузки над макетом. Ключа нет вне выгрузки и если хоть один UUID не найден. Состав определяемого типа отдаётся в записи `typeCompositions` с тем же UUID ([ниже](#составы-определяемых-типов-и-характеристик-typecompositions)).
- `stringQualifiers` (`length`, `allowedLength`), `numberQualifiers` (`digits`, `fractionDigits`, `allowedSign`), `dateQualifiers` (`dateFractions`), `binaryDataQualifiers` — только записанные; значения перечислений — имена констант (`VARIABLE`, `NONNEGATIVE`, `DATE_TIME`).
- `editable` и `readOnlyReason`. Правится только белый словарь: `xs:string`, `xs:decimal`, `xs:dateTime`, `xs:boolean`, `v8:StandardPeriod`, `v8:UUID`; ссылки `cfg:<Вид>Ref.<Имя>` и наборы `cfg:<Вид>Ref` видов Catalog, Document, Enum, ChartOfCharacteristicTypes, ChartOfAccounts, ChartOfCalculationTypes, ExchangePlan, BusinessProcess, Task; «любая ссылка» `cfg:AnyIBRef` (до 2.16 и в проекте EDT — `cfg:AnyRef`); `cfg:Characteristic.<ПВХ>`; один определяемый тип с найденным именем без других типов. Всё прочее — `v8:Type`, `v8:Null`, `v8:ValueTable`, `v8:ValueStorage`, `v8:StandardBeginningDate`, `v8:ValueListType`, типы чужих пространств, `DocumentJournalRef` (у журналов ссылочного типа нет), `BusinessProcessRoutePointRef`, неизвестный UUID, определяемый тип вне выгрузки, `binaryDataQualifiers` — `editable: false` с причиной: такой тип переносится только эхом. Тип поля вложенного набора объединения тоже только читается (мутации эти поля не адресуют).
- Вне выгрузки (внешний отчёт, отдельный файл) записанные ссылочные типы читаются как правимые: их можно снять, но новые не предлагаются.

### Составы определяемых типов и характеристик: typeCompositions

Определяемый тип в схеме записан одним UUID (`typeIds`), характеристика — набором `cfg:Characteristic.<ПВХ>` (`typeSets`); их состав лежит в описании другого объекта конфигурации. `cf-dcs-info` отдаёт составы отдельным ключом верхнего уровня:

```json
"typeCompositions": [
  {"source": "9a33b5dc-a8f1-496e-9961-95890984cd86", "name": "ЗначениеДоступа",
   "types": ["cfg:CatalogRef._ДемоФизическиеЛица", "cfg:CatalogRef._ДемоКассыККМ", "…"], "typeSets": []},
  {"source": "cfg:Characteristic.РазделыДатЗапретаИзменения",
   "types": ["cfg:CatalogRef._ДемоБанковскиеСчета", "…"], "typeSets": []}]
```

- `source` — UUID из `typeIds` (текстом первого вхождения в файле; тот же UUID другим регистром — та же запись) либо набор `cfg:DefinedType.<Имя>` или `cfg:Characteristic.<ПВХ>` из `typeSets`. `name` — имя определяемого типа, только у записи по UUID.
- `types`, `typeSets` — раскрытый состав без квалификаторов (квалификаторы есть у `definedTypes[].composition` словаря `cf-dcs-type-dictionary`). Раскрытие то же, что у словаря и `cf-md-query-tables` (`TypeCompositions`): определяемый тип — тип из описания `DefinedTypes/<Имя>` выгрузки или проекта EDT, характеристика — тип значения плана видов характеристик; вложенные наборы подставляются своим составом, набор, замыкающий цикл, и набор без описания остаются в `typeSets`; наборы вида (`cfg:CatalogRef`) и «любая ссылка» не раскрываются.
- Запись — в форме своей схемы: в выгрузках до 2.16 и проектах EDT «любая ссылка» в составе — `cfg:AnyRef`, как в `valueType` той же схемы (у `cf-md-query-tables` — запись конфигуратора `cfg:AnyIBRef` и для EDT).
- Порядок записей — первого вхождения при чтении: поля наборов (поле объединения раньше полей его вложенных наборов), вычисляемые поля, параметры. Повторный тип записи не дублирует.
- Ключа нет, если в типах нет определяемых типов и характеристик, схема вне выгрузки или ни одно описание не найдено; запись ненайденного типа (неизвестный UUID, нет файла описания, пустой тип) не появляется, отказа нет. Типы вложенных схем (`nestedSchemas`) не раскрываются.
- `valueType` составов не несёт: его ключи ровно те, что принимает писатель типов, поэтому эхо прочитанного типа в `cf-dcs-set-field`, `cf-dcs-set-calculated-field` и `cf-dcs-set-parameter` остаётся байтовым no-op.

### Значение параметра: valueTyped

`value` параметра — лексический текст из модели: строка, поле и ссылка конфигуратора в нём неразличимы, а ссылка (`dcscor:DesignTimeValue`), стандартный период и `xsi:nil` текста не дают. `valueTyped` читается из текста файла и отдаёт значение той же формой, что `cf-dcs-settings-info` у значений настроек ([«Значения: белый список записи»](#значения-белый-список-записи)):

```json
{"type": "v8:StandardPeriod", "period": {"variant": "Custom", "startDate": "0001-01-01T00:00:00", "endDate": "0001-01-01T00:00:00"}}
{"nil": true}
{"type": "xs:boolean", "text": "false", "decoded": false}
{"type": "xs:decimal", "text": "1", "decoded": 1}
{"type": "xs:dateTime", "text": "0001-01-01T00:00:00"}
{"type": "xs:string"}
{"type": "dcscor:DesignTimeValue", "text": "Справочник.Пользователи.ПустаяСсылка"}
{"type": "v8:UUID", "text": "00000000-0000-0000-0000-000000000000"}
{"type": "v8:ValueListType", "list": {"items": [{"value": {"type": "xs:string", "text": "USD"}}, {"value": {"type": "xs:string", "text": "EUR"}}]}}
```

- `type` — `xsi:type` дословно; пустая строка — `{"type": "xs:string"}` без `text`; `xsi:nil` — `{"nil": true}`.
- **Список значений — повторяющиеся `value`.** Платформа хранит список параметра схемы не элементом `v8:ValueListType`, а элементами `value` подряд, без представлений: список `USD` («Доллар»), `EUR` после загрузки выгружается как `<value xsi:type="xs:string">USD</value><value xsi:type="xs:string">EUR</value>`. Чтение отдаёт такие `value` формой списка (`{type: "v8:ValueListType", list: {items: [{value}]}}`, без `presentation`): при нескольких `value` и при одном у параметра с `valueListAllowed: true`. Один `value` без списка значений — само значение. Элемент `v8:ValueListType` в `value` читается как записан, с представлениями: `presentation` у элементов `valueTyped.list.items` бывает только у такой записи. Запись её не разворачивает и не меняет, а строгая проверка при `valueListAllowed: true` предупреждает о ней (вид `valueListPresentationsLost`, см. [«Строгая проверка схемы»](#строгая-проверка-схемы)).
- `v8:UUID` у параметра схемы пишется, поэтому в `valueTyped` он без `opaque` (в настройках он `opaque`). Прочие типы вне белого списка записи — с `opaque: true`.
- Строки `v8:LocalStringType` — на языке конфигурации, как у записи значения.
- **Эхо — без записи.** `valueTyped`, отправленный обратно как `value` в `cf-dcs-set-parameter`, файл не трогает: значение сравнивается с записанным по смыслу (ключи с `null` не считаются, числа по величине; список со всеми `value` параметра). Так эхо переживают список выгрузки, элемент `v8:ValueListType` со служебными `valueType`/`lastId` и представлениями и строка на нескольких языках. Эхо значения равносильно отсутствию `value` в payload: при смене типа записанное значение сверяется с новым типом. Значение `opaque` эхом не считается — его правка, как и у настроек, отказ «доступно только для чтения».

`cf-dcs-type-dictionary` — всё, что окно типа предлагает новым типом. Вход: `objectXml` (файл схемы), `schemaVersion` (`V2_xx`; у `Template.dcs` необязателен). Ответ:

```json
{"configurationFound": true, "anyRef": "cfg:AnyIBRef",
 "primitives": [{"type": "xs:string", "label": "Строка", "qualifiers": "string"}, {"type": "xs:boolean", "label": "Булево"}],
 "refKinds": [{"kind": "Catalog", "label": "Справочник", "platformName": "СправочникСсылка",
   "typeSet": "cfg:CatalogRef", "types": ["cfg:CatalogRef.Валюты"]}],
 "characteristics": ["cfg:Characteristic.ВидыСубконто"],
 "definedTypes": [{"name": "ДенежнаяСуммаЛюбогоЗнака", "typeId": "…",
   "composition": {"types": ["xs:decimal"], "typeSets": [], "typeIds": [],
     "numberQualifiers": {"digits": "15", "fractionDigits": "2", "allowedSign": "ANY"}}}]}
```

- `primitives[]` — шесть примитивов словаря; `qualifiers` — `string` | `number` | `date`, у прочих ключа нет.
- `refKinds[]` — виды в порядке словаря, только с объектами; `label` — из той же таблицы, что `objectKinds` у `cf-enum-labels`; `types` — по имени.
- `anyRef` — `cfg:AnyIBRef` в выгрузке начиная с формата 2.16 (8.3.23), `cfg:AnyRef` в более ранней выгрузке и у `Template.dcs` 1С:EDT.
- `definedTypes[].composition` — состав определяемого типа формой `valueType` из `cf-dcs-info`: `types[]`, `typeSets[]`, пустой `typeIds[]` и записанные квалификаторы; без `editable`/`readOnlyReason`, состав правится в конфигураторе. По `types`/`typeSets` сверяется значение параметра при записи ([«Запись типа значения»](#запись-типа-значения)). Источник: в выгрузке `DefinedTypes/<Имя>.xml` (элемент `Type`, квалификаторы читаются моделью формата `schemaVersion`), в проекте EDT `DefinedTypes/<Имя>/<Имя>.mdo` (корневой `type`; имена EDT переводятся в запись конфигуратора, как у свойств объектов EDT: `BinaryData` → `xs:base64Binary`, `CatalogRef` → набор `cfg:CatalogRef`; незаписанные квалификаторы получают умолчания метамодели). Вложенные наборы раскрываются, как в `typeCompositions`; повторы убираются, порядок: свои типы, затем типы вложенных наборов. Типы объектов вне белого словаря (`cfg:CatalogObject.…`, наборы записей) отдаются как есть. Нет описания, типа в нём или тип пуст: ключа нет. Ответ проекта EDT совпадает с выгрузкой, кроме «любой ссылки» (`cfg:AnyRef`).
- Вне выгрузки — `configurationFound: false`, `refKinds`, `characteristics` и `definedTypes` пустые: новыми бывают только примитивы.

## Мутации

| Операция (`apply-mutation`) | Вход кроме `objectXml`/`schemaVersion` | Поведение |
|---|---|---|
| `cf-dcs-add-data-set` | `name`, `type` (`query` \| `object` \| `union`), `dataSource` | минимальный набор на место по порядку корня |
| `cf-dcs-remove-data-set` | `name` | отказ, если на набор ссылаются связи |
| `cf-dcs-rename-data-set` | `name`, `newName` | каскад по `sourceDataSet`/`destinationDataSet` связей |
| `cf-dcs-set-data-set-props` | `name`, `payloadJson` `{autoFillFields?, dataSource?, objectName?}` | точечная замена/вставка/снятие подэлементов |
| `cf-dcs-set-query` | `tag` (имя набора верхнего уровня или путь `Объединение/Вложенный`; пусто — единственный набор-запрос схемы), `payloadJson` — текст запроса | замена текста `<query>` с переводом строки файла; эхо — no-op |
| `cf-dcs-add-field` | `dataSet`, `payloadJson` `{dataPath, field, title?}` | `DataSetFieldField` в позицию `field*` набора |
| `cf-dcs-set-field` | `dataSet`, `dataPath`, `payloadJson` `{newDataPath?, field?, title?, useRestriction?, attributeUseRestriction?, role?, valueType?}` | правка подэлементов поля по sequence |
| `cf-dcs-remove-field` | `dataSet`, `dataPath` | удаление обычного поля |
| `cf-dcs-autofill-fields` | `dataSet` (имя или путь `Объединение/Вложенный`, как у `cf-dcs-set-query`) | недостающие поля по списку выборки последнего запроса выборки пакета; ответ `{added, skipped}`, см. [«Автозаполнение полей по запросу»](#автозаполнение-полей-по-запросу) |
| `cf-dcs-add-link` | `payloadJson` `{sourceDataSet, destinationDataSet, sourceExpression, destinationExpression, parameter?, parameterListAllowed?, linkConditionExpression?, startExpression?, required?}` | связь на место по порядку корня; наборы должны существовать; `required` и `parameterListAllowed` см. [«Связи наборов»](#связи-наборов) |
| `cf-dcs-set-link` | `index`, `payloadJson` с теми же полями | правка связи по порядковому номеру; `required` и `parameterListAllowed` см. [«Связи наборов»](#связи-наборов) |
| `cf-dcs-remove-link` | `index` | удаление связи по номеру |
| `cf-dcs-add-calculated-field` | `payloadJson` `{dataPath, expression, title?}` | вычисляемое поле после наборов, связей и существующих вычисляемых полей |
| `cf-dcs-set-calculated-field` | `dataPath`, `payloadJson` `{newDataPath?, expression?, title?, valueType?}` | правка вычисляемого поля |
| `cf-dcs-remove-calculated-field` | `dataPath` | удаление вычисляемого поля |
| `cf-dcs-add-total-field` | `payloadJson` `{dataPath, expression, groups?[]}` | ресурс на место по порядку корня |
| `cf-dcs-set-total-field` | `index`, `payloadJson` `{dataPath?, expression?, groups?}` | правка ресурса по порядковому номеру |
| `cf-dcs-remove-total-field` | `index` | удаление ресурса по номеру |
| `cf-dcs-add-parameter` | `payloadJson` `{name, title?, expression?, use?, useRestriction?, valueType?, value?}` | параметр на место по порядку корня |
| `cf-dcs-set-parameter` | `name`, `payloadJson` `{newName?, title?, expression?, use?, useRestriction?, valueType?, value?, valueListAllowed?, availableAsField?, denyIncompleteValues?}` | правка параметра по имени |
| `cf-dcs-remove-parameter` | `name` | удаление параметра по имени |

Общие правила `set`-операций: ключи, которых нет в `payloadJson`, не трогаются; неизвестный ключ — отказ; пустой `payloadJson` — ничего не меняется. Необязательный подэлемент снимается значением `null` (строковый — и пустым текстом), обязательные по формату (`dataPath`, `field`, `expression`, имена наборов и параметров) требуют непустую строку. Новое имя или путь, занятые другим элементом того же вида, — отказ; имена наборов, пути полей и вычисляемых полей и имена параметров сравниваются без учёта регистра (см. [«Имена без учёта регистра»](#имена-без-учёта-регистра)).

Эхо прочитанного — байтовый no-op: значение, равное записанному (обязательный текстовый подэлемент — с точностью до переводов строк, заголовок и представление варианта — по строке, которую отдаёт чтение), оставляет исходные байты; если правка не изменила ни байта, файл не переписывается. Так эхо переживают и формы, которые запись сама не пишет: заголовок формой `xs:string` или на нескольких языках, заголовок из одного пробела (новый пробельный заголовок снимает элемент как пустой), представление варианта формой `xs:string`.

### Многострочный текст

Текст элемента пишется дословно и так же читается `cf-dcs-info` и `cf-dcs-settings-info`: пустые строки, ведущие табуляции строк и пробелы в конце сохраняются. Это касается всех значений, выражений, заголовков и представлений схемы и вариантов настроек.

- **Отступы — только у разметки.** Новый или заменяемый фрагмент раскладывается по строкам с отступом места: перевод строки и отступ получает каждый тег, перед которым стоит тег; текст остаётся в строке своего тега, продолжения его строк отступа не получают.
- **Пробельное значение — текст.** Пробелы с переводом строки между тегами — разметка исходника, она расставляется заново; но единственное содержимое элемента (`<value xsi:type="xs:string">` + перевод строки + `</value>`) — значение: пустой элемент платформа пишет самозакрытым.
- **Переводы строк — файловые.** `\r\n`, одиночные `\r` и `\n` текста приводятся к переводу строки файла (CRLF, если он в файле есть, иначе LF). XML-разбор нормализует любой перевод строки в LF, поэтому чтение отдаёт текст с `\n`, а выгрузка хранит многострочный текст CRLF-файла с CRLF.

Пользовательские поля вариантов (`userFields`) только читаются — их выражения не пишутся.

### Имена без учёта регистра

Встроенный язык и выражения схемы регистр имён не различают: `Сумма` и `СУММА` — одно поле. Поэтому, как имена параметров ([«Параметры»](#параметры)) и вариантов настроек, без учёта регистра сверяются:

| Что | Операции | Отказ |
|---|---|---|
| имя набора данных верхнего уровня | `cf-dcs-add-data-set` | «Набор данных «основнойзапрос» уже есть в схеме: «ОсновнойЗапрос».» |
| | `cf-dcs-rename-data-set` (`newName`) | «Имя «ОСНОВНОЙЗАПРОС» уже занято: набор данных «ОсновнойЗапрос» уже есть в схеме.» |
| путь к данным поля среди полей своего набора | `cf-dcs-add-field` | «Поле «выявлено» уже есть в наборе: «Выявлено».» |
| | `cf-dcs-set-field` (`newDataPath`) | «Путь к данным «видпроверки» уже занят: поле «ВидПроверки» уже есть в наборе.» |
| путь к данным вычисляемого поля среди вычисляемых полей корня | `cf-dcs-add-calculated-field` | «Вычисляемое поле «расшифровкаполя» уже есть в схеме: «РасшифровкаПоля».» |
| | `cf-dcs-set-calculated-field` (`newDataPath`) | «Путь к данным «Х» уже занят: вычисляемое поле «х» уже есть в схеме.» |

- Смена регистра своего имени разрешена (`ВнешняяТаблица` → `ВНЕШНЯЯТАБЛИЦА`, у набора — с каскадом по связям), своё имя тем же текстом — no-op.
- Точное совпадение даёт тот же отказ: «Набор данных «ОсновнойЗапрос» уже есть в схеме: «ОсновнойЗапрос».».
- Адресация точная: поле, набор и вычисляемое поле в `cf-dcs-set-*`/`cf-dcs-remove-*` ищутся по точному имени.
- Что не сверяется: путь ресурса (в формате он не уникален — одно поле считается разными выражениями по разным группировкам), имена вложенных наборов объединений (их мутации не добавляют; одно имя бывает в двух объединениях одной схемы), совпадение пути вычисляемого поля с полем набора (платформа такое пишет).

### Наборы данных

`cf-dcs-add-data-set` пишет минимальный набор, как его создаёт конфигуратор: у запроса — источник и пустой `<query/>` (элемента `autoFillFields` нет: отсутствие и есть `true`), у объекта — `objectName`, равный имени набора, объединение — пустым контейнером с одним именем. Набор встаёт после последнего набора, иначе после источников данных.

`cf-dcs-set-data-set-props` знает подэлементы `autoFillFields`, `dataSource` и `objectName`; подэлемент, которого у вида набора нет по формату (например, `objectName` у запроса), — отказ. `autoFillFields` пишется, как у платформы: `false` — элементом, `true` и `null` — снятием элемента.

`cf-dcs-remove-data-set` отказывает, пока на набор ссылаются связи: «Набор данных … упомянут в связях наборов (2): сначала удалите эти связи.» `cf-dcs-rename-data-set` правит имя и каскадно все ссылки в связях.

`cf-dcs-set-query` принимает текст запроса как есть (не JSON) в `payloadJson`; набор — поле `tag`, без него правится единственный набор-запрос схемы (верхнего уровня или внутри объединения), при нескольких — отказ «укажите имя набора».

- **Переводы строк** приводятся к переводу строки файла, как у [многострочного текста](#многострочный-текст). Текст, совпадающий с записанным с точностью до переводов строк и экранирования, файл не трогает.
- **Наборы внутри объединений.** `tag` принимает путь `Объединение/Вложенный` любой вложенности, разделитель `/`, пробелы вокруг звеньев не важны: имя вложенного набора уникально только внутри своего объединения. Имя без `/` ищет набор верхнего уровня; если такое имя есть только внутри объединений, отказ «не найден» перечисляет пути, которыми его адресовать. Путь к самому объединению — отказ «… — объединение: своего запроса у него нет, укажите путь к вложенному набору-запросу», к набору-объекту — отказ «объект, а не запрос». Наборы вложенных схем (`nestedSchema`) операция не адресует.

```json
{"op": "cf-dcs-add-data-set", "objectXml": "…/Ext/Template.xml", "schemaVersion": "V2_20",
 "name": "Остатки", "type": "query", "dataSource": "ИсточникДанных1"}
```

### Поля наборов

Операции полей работают только с обычными полями (`DataSetFieldField`); папка полей и поле-вложенный набор — отказ. Поле адресуется именем набора верхнего уровня и путём к данным. Поля вложенных наборов объединения только читаются: имя вложенного набора в `cf-dcs-set-field` — отказ; дописывать их умеет только `cf-dcs-autofill-fields` ([«Автозаполнение полей по запросу»](#автозаполнение-полей-по-запросу)). Поля самого объединения правятся как обычно. `valueType` см. [«Запись типа значения»](#запись-типа-значения), сверку путей см. [«Имена без учёта регистра»](#имена-без-учёта-регистра).

`useRestriction` и `attributeUseRestriction` принимают объект с флагами `field`, `condition`, `group`, `order`; `role` — объект со свойствами роли (флаги `dimension`, `account`, `balance`, `ignoreNullValues`, `required`, `dimensionAttribute`, `isMain`; строки `parentDimension`, `accountTypeExpression`, `balanceGroupName`, `accountField`; целое `periodNumber`; перечисления `periodType` — `Main` | `Specify` | `Additional`, `balanceType` и `accountingBalanceType` — `None` | `OpeningBalance` | `ClosingBalance`). Блок заменяется целиком и пишется, как у платформы: только взведённые флаги, дети роли — в пространстве `dcscom`; без единого взведённого значения элемент снимается, `null` тоже снимает.

- **Имя группы остатка при `balance`.** При `balance: true` платформа хранит `balanceGroupName` сразу после `balance`, а без имени пишет пустой `<dcscom:balanceGroupName/>`. Запись делает так же: пустое, пробельное или отсутствующее имя при взведённом `balance` пишется самозакрытым элементом, непустое как задано. Чтение пустое имя не отдаёт, эхо роли — байтовый no-op. Без `balance` пустое имя не пишется (снятие `balance` уносит и его). Если в файле `balance` без имени группы, эхо поля файл не меняет, а любая настоящая правка поля дописывает пустое имя сразу после `balance`.

```json
{"op": "cf-dcs-set-field", "objectXml": "…", "schemaVersion": "V2_20",
 "dataSet": "ОсновнойЗапрос", "dataPath": "Сумма",
 "payloadJson": "{\"title\":\"Сумма документа\",\"useRestriction\":{\"group\":true},\"role\":{\"balance\":true,\"balanceType\":\"ClosingBalance\"}}"}
```

### Связи наборов

У связи в формате нет ключа, поэтому `cf-dcs-set-link` и `cf-dcs-remove-link` адресуются порядковым номером `dataSetLink` в файле с нуля (поле `index`); номера берутся из `cf-dcs-info`, перечитанного после предыдущей правки. Наборы в `sourceDataSet` и `destinationDataSet` должны существовать на верхнем уровне схемы. Чтение отдаёт только записанное в файл.

**Обязательность связи (`required`) платформа не хранит.** XSD элемент допускает, но загрузка отбрасывает записанный `<required>true</required>`. Поэтому:

- `cf-dcs-add-link` с `required: true` — отказ «Обязательность связи наборов (required=true) не записать: загрузка платформы … этот флаг не хранит …». `false` и `null` элемента не пишут.
- `cf-dcs-set-link` с `required: true` у связи, где флаг не записан, — тот же отказ. Эхо записанного в файле `true` — без правки: при правке других свойств связи флаг молча не снимается. `false` и `null` снимают элемент; записанный `<required>false</required>` при эхе `false` остаётся на месте, чтобы эхо было байтовым no-op.
- `required` в `cf-dcs-info` есть, только если записан в файле.

**Флаг списка у связи с параметром (`parameterListAllowed`) записан всегда.** У связи с `parameter` без `parameterListAllowed` платформа выгружает явный `<parameterListAllowed>false</parameterListAllowed>`, а записанный `true` сохраняет. Запись делает так же:

- `cf-dcs-add-link` с непустым `parameter` без `parameterListAllowed` (или с `null`) пишет `<parameterListAllowed>false</parameterListAllowed>` сразу после `parameter`, на место по xs:sequence. Явные `true` и `false` — как заданы. Без `parameter` и с пустым `parameter` незаданный флаг не пишется.
- `cf-dcs-set-link`: если после правки у связи есть непустой `parameter` (из payload или из файла), недостающий флаг дописывается `false` вместе с настоящей правкой связи, в том числе с заданием `parameter`; эхо файл не трогает. `null` у такой связи означает `false`, а не снятие элемента. Явные `true` и `false` — как заданы.

**Флаг списка без параметра (`parameterListAllowed` у связи без `parameter`) платформа не хранит**: загрузка отбрасывает его и с `false`, и с `true`. Поэтому, как у `required`:

- `cf-dcs-add-link` с `parameterListAllowed: true` без непустого `parameter` — отказ «Флаг «Список параметров» связи наборов (parameterListAllowed=true) без параметра связи не записать: …». `false` и `null` без параметра не пишутся.
- `cf-dcs-set-link`, если после правки у связи нет непустого `parameter` (из payload или из файла):
  - снятие записанного `parameter` (`null` или пустая строка) снимает и флаг; `parameterListAllowed: true` в том же payload — отказ;
  - `parameterListAllowed: true` у связи без параметра — тот же отказ, кроме эха записанного `true`;
  - `false` и `null` снимают элемент, если он есть; записанный `<parameterListAllowed>false</parameterListAllowed>` при эхе `false` остаётся на месте;
  - правка других свойств связи записанный флаг не трогает. Пустой `parameter` у связи, где параметра не было, — эхо, а не снятие.
- Эхо любой связи — байтовый no-op. Строгая проверка называет связь с флагом без параметра (вид `linkListFlagWithoutParameter`, см. [«Строгая проверка схемы»](#строгая-проверка-схемы)).

```json
{"op": "cf-dcs-add-link", "objectXml": "…", "schemaVersion": "V2_20",
 "payloadJson": "{\"sourceDataSet\":\"ОсновнойЗапрос\",\"destinationDataSet\":\"Остатки\",\"sourceExpression\":\"Номенклатура\",\"destinationExpression\":\"Номенклатура\",\"parameter\":\"Номенклатура\",\"parameterListAllowed\":false}"}
```

### Вычисляемые поля

Адресация по пути к данным (`dataPath`); новый путь не должен совпадать с путём другого вычисляемого поля без учёта регистра ([«Имена без учёта регистра»](#имена-без-учёта-регистра)). `cf-dcs-set-calculated-field` правит путь, выражение, заголовок и тип значения (`valueType`, [«Запись типа значения»](#запись-типа-значения)); остальные подэлементы (ограничения, оформление) не трогаются.

### Ресурсы (итоговые поля)

Путь к данным ресурса в формате не уникален — одно поле может считаться разными выражениями по разным группировкам, поэтому путь не сверяется с другими ресурсами, а `cf-dcs-set-total-field` и `cf-dcs-remove-total-field` адресуются порядковым номером `totalField` в файле с нуля. `groups` заменяет элементы `group` целиком списком в его порядке; пустой список и `null` снимают все группировки (итог по всем группировкам).

```json
{"op": "cf-dcs-add-total-field", "objectXml": "…", "schemaVersion": "V2_20",
 "payloadJson": "{\"dataPath\":\"Сумма\",\"expression\":\"Сумма(Сумма)\",\"groups\":[\"Организация\"]}"}
```

### Параметры

Адресация по имени (точное совпадение). Имена параметров сравниваются без учёта регистра: в тексте запроса `&Размер` и `&размер` — один параметр, поэтому `cf-dcs-add-parameter` с именем, которое уже есть в схеме другим регистром, — отказ «Параметр «размер» уже есть в схеме: «Размер».», а `newName`, совпадающий без учёта регистра с именем другого параметра, — отказ «Имя «РАЗМЕР» уже занято: параметр «Размер» уже есть в схеме.». Смена регистра собственного имени (`Размер` → `РАЗМЕР`) разрешена. `use` принимает `Always` или `Auto`; `Auto` платформа не пишет — элемент снимается, это значение по умолчанию. `useRestriction` — булево и пишется, как задано: платформа хранит и `true`, и `false`. Тип, значение и признаки параметра — в [«Запись типа значения»](#запись-типа-значения).

**Форма платформы: `value` и `useRestriction` у каждого параметра.** Платформа пишет `useRestriction` у каждого параметра (без значения — явным `false`), а `value` — у каждого параметра без списка значений (без значения — `<value xsi:nil="true"/>`, в том числе при `expression` и без `valueType`); у параметра со списком (`valueListAllowed: true`) пустой список хранится без единого `value`. Параметры без этих элементов загрузка дополняет ими. Поэтому:

- `cf-dcs-add-parameter` пишет `value` и `useRestriction` всегда: без `value` в payload — `xsi:nil`, без `useRestriction` — `false`. Минимальный параметр (например, от конструктора запроса) — имя, `<value xsi:nil="true"/>` и `<useRestriction>false</useRestriction>`.
- `cf-dcs-set-parameter`: `useRestriction: null` пишет `false`; любая настоящая правка параметра дописывает недостающие `value` (`xsi:nil`, если списка нет) и `useRestriction` (`false`) на их места по xs:sequence. Эхо файл не трогает.

```json
{"op": "cf-dcs-add-parameter", "objectXml": "…", "schemaVersion": "V2_20",
 "payloadJson": "{\"name\":\"Период\",\"title\":\"Период отчёта\",\"use\":\"Always\",\"useRestriction\":false}"}
```

### Запись типа значения

`valueType` в `cf-dcs-set-field`, `cf-dcs-set-calculated-field`, `cf-dcs-set-parameter` и `cf-dcs-add-parameter` — та же форма, что отдаёт `cf-dcs-info` ([«Типы значений»](#типы-значений)), либо `null`. Порядок `types` и `typeSets` в payload — порядок записи; `editable` и `readOnlyReason` на входе не читаются. Числа квалификаторов принимаются строкой или числом JSON, перечисления — именами констант (`VARIABLE`) или текстом файла (`Variable`). Определяемый тип задаётся `typeIds` (UUID) или по имени — `definedTypes` (UUID ищется по `DefinedTypes` выгрузки над макетом); если заданы оба, списки должны совпасть.

- **Эхо — без записи.** Тип сравнивается с записанным по смыслу: те же элементы в том же порядке и те же квалификаторы (префиксы нормализованы, `"0"` и `0` — одно число). Совпал — элемент не трогается, поэтому эхо `cf-dcs-info` — байтовый no-op, и тип вне словаря (`editable: false`) переносится только так.
- **Байты платформы.** Каждый ребёнок `valueType` на своей строке с отступом по месту; порядок `Type` → `TypeSet` → `TypeId` → `NumberQualifiers` → `StringQualifiers` → `DateQualifiers`; `xs:`/`v8:` без своих объявлений (они есть в корне схемы); тип конфигурации — с объявлением префикса на самом элементе: `<v8:Type xmlns:d4p1="…/current-config">d4p1:CatalogRef.Валюты</v8:Type>`, где число — глубина элемента от корня схемы (у параметра и вычисляемого поля `d4p1`, у поля набора `d5p1`); `TypeId` — голый UUID. Тип, прочитанный и записанный заново, совпадает с исходными байтами.
- **Снятие.** `null` и тип без единого элемента снимают `valueType` целиком: пустого `<valueType/>` платформа не пишет.
- **Порядок типов составного типа.** Загрузка платформы хранит составной тип в своём порядке (`v8:Type`, затем `v8:TypeSet`, затем `v8:TypeId`; внутри серий по своим ключам типов), поэтому выгрузка после загрузки может отличаться от записанного порядком элементов `valueType`.
- **Белый словарь.** Пишутся только примитивы `xs:string`, `xs:decimal`, `xs:dateTime`, `xs:boolean`, `v8:StandardPeriod`, `v8:UUID`; ссылки `cfg:<Вид>Ref.<Имя>` и наборы `cfg:<Вид>Ref` видов словаря; «любая ссылка» формата файла (`cfg:AnyIBRef`, в `Template.dcs` — `cfg:AnyRef`); `cfg:Characteristic.<ПВХ>`; один определяемый тип.
- **Отказы:** тип вне словаря (`xs:int`, `v8:ValueTable` и т. п.; записанный — «Тип «…» правится в конфигураторе: редактор переносит такой тип только без изменений.»); `DocumentJournalRef` — «у журнала документов нет ссылочного типа»; «любая ссылка» чужого формата; повтор элемента; новая ссылка, набор вида или характеристика вне выгрузки конфигурации (вне выгрузки новыми бывают только примитивы и «любая ссылка», записанные в этом же `valueType` элементы сохраняются) и объект, которого нет в составе выгрузки (`Configuration.xml` или `Configuration.mdo`); определяемый тип вместе с другими типами (платформа такой составной тип хранит, запись его не пишет), неизвестный или вне выгрузки; квалификатор без своего типа и примитив без квалификатора (`xs:string` — `stringQualifiers {length, allowedLength}`, `xs:decimal` — `numberQualifiers {digits, fractionDigits, allowedSign}`, `xs:dateTime` — `dateQualifiers {dateFractions}`, все поля обязательны); нецелые и отрицательные числа, дробная часть больше разрядности, разрядность больше 64 (см. ниже); `binaryDataQualifiers`; неизвестный ключ.
- **Границы квалификаторов.** Разрядность числа до 64 платформа хранит как записано, а большую молча обрезает до 64, поэтому новый тип с разрядностью больше 64 — отказ «Разрядность числа (65) больше 64: платформа сохранит только 64 разряда.»; дробная часть, равная разрядности, хранится как записана. Длина строки сверху не ограничена. Проверяется только изменённый тип: эхо записанного типа с разрядностью больше 64 — no-op.

У параметра рядом с типом:

- `value` — значение формой значений настроек ([«Значения: белый список записи»](#значения-белый-список-записи)), плюс `{"type": "v8:UUID", "text": "…"}`; `{"nil": true}` и `null` — «значение не задано»: у параметра без списка значений это `xsi:nil`, у параметра со списком — ни одного `value`. Значение, равное записанному по смыслу (эхо `valueTyped` из `cf-dcs-info`), файл не трогает — см. [«Значение параметра: valueTyped»](#значение-параметра-valuetyped). Значения правятся зоной: все `value` параметра заменяются новыми целиком.
- Список значений (`{"type": "v8:ValueListType", "list": {"items": [{"value": …}]}}`) пишется формой платформы: повторяющимися `value` подряд, перед `useRestriction`, без `v8:ValueListType`, `valueType`/`lastId` и представлений. Список допустим только при итоговом `valueListAllowed: true` (в payload или в файле), иначе отказ «Список значений у параметра схемы пишется только при valueListAllowed=true…»; `cf-dcs-add-parameter` списка не принимает («Список значений задаётся у созданного параметра…»). Представления значений параметра платформа не хранит, поэтому представление элемента — отказ «Представление «…» элемента списка значений не записать: …»; пустая строка представлением не считается. Элементы — простые скаляры и `v8:UUID`; пустой список — ни одного `value`. `{"nil": true}` пишется `<value xsi:nil="true"/>` только единственным элементом списка: одиночный `xsi:nil` платформа хранит и отличает от пустого списка, а рядом с другими значениями отбрасывает. Поэтому `nil` (в том числе с `"type": "v8:UUID"`) в списке из двух и более элементов — отказ «Элемент «значение не задано» (nil) рядом с другими элементами списка значений не записать…»; один `xsi:nil` у параметра со списком читается списком `[nil]`. Уже записанный список с `nil` среди других элементов читается как есть, эхо и правка соседних свойств его не трогают. `null` и `{"nil": true}` всем значением при списке — пустой список. Каждый элемент должен подходить к типу; пустая строка у элемента списка «не задано» не означает и подходит только к строке. Элемент `v8:ValueListType` с представлениями запись не разворачивает: эхо и правка других свойств параметра переносят его как есть, о потере представлений предупреждает [строгая проверка](#строгая-проверка-схемы).
- Значение должно подходить к типу: `xsi:nil` и пустая строка (`<value xsi:type="xs:string"/>`) — к любому (пустой строкой платформа хранит «значение не задано» и у параметров других типов; к элементам списка это не относится); `xs:*`, стандартные период и дата начала, UUID — к тому же типу; ссылка конфигуратора (`dcscor:DesignTimeValue`, `Справочник.Имя.Значение`) — к ссылке того же объекта, набору его вида или «любой ссылке»; определяемый тип — по его составу из `DefinedTypes` выгрузки или проекта EDT, без найденного описания подходит только «не задано»; список значений — каждым элементом; параметр без типа принимает любое. Если тип меняется, а `value` в payload нет, сверяется значение в файле: несовместимое — отказ «Значение параметра не подходит к новому типу: укажите значение или очистите его».
- `valueListAllowed`, `availableAsField`, `denyIncompleteValues` — булевы; значение по умолчанию (`false`, `true`, `false`) пишется снятием элемента, иное — элементом; `null` снимает элемент. Совпадающее с файлом значение файл не трогает, даже если умолчание записано явно (эхо). Явно записанные умолчания, как и `use=Auto`, платформа при загрузке не хранит.
- Включение списка значений (`valueListAllowed: true`) снимает `xsi:nil`: пустой список платформа хранит без `value`. Выключение списка без значений дописывает `xsi:nil`, с одним элементом `value` оставляет его, а с несколькими элементами `value` без нового `value` в том же payload — отказ «…снять valueListAllowed можно, только задав в том же payload одно значение value». Считаются элементы `value`: список одним элементом `v8:ValueListType` — один элемент, поэтому снятие признака у него проходит, а элемент остаётся байт в байт.

```json
{"op": "cf-dcs-set-parameter", "objectXml": "…", "schemaVersion": "V2_20", "name": "Организация",
 "payloadJson": "{\"valueType\":{\"types\":[\"cfg:CatalogRef.Организации\"]},\"value\":{\"nil\":true},\"availableAsField\":false}"}
```

## Варианты настроек

Вариант настроек — `settingsVariant` корня схемы: настройки компоновки, которые пользователь видит как «вариант отчёта». Операции раздела читают вариант целиком и правят структуру (группировки, таблицы, диаграммы), выбранные поля, отбор, сортировку, поля группировки, условное оформление и параметры данных и вывода.

### Чтение: cf-dcs-settings-info

Вход: `objectXml`, `schemaVersion` и необязательное имя `variant`.

- Без `variant` — список вариантов `{"variants":[{"name":"…","presentation":"…"}]}`; представление — строка на языке конфигурации. В список попадают только прямые дети корня схемы: варианты вложенных схем из корня не видны и не адресуются.
- С `variant` — тот же список из одного варианта с полем `settings` (загрузка ленивая). Вариант не найден или имя встречается в файле дважды (XSD уникальность имён не контролирует) — отказ.

Ключи DTO необязательны и присутствуют, только когда записаны в файл; `xsi:type` значений читается из текста файла дословно (после JAXB `xs:string`, `dcscor:Field` и `dcscor:DesignTimeValue` неразличимы).

`settings` — корень настроек варианта:

| Ключ | Содержимое |
|---|---|
| `userFields` | пользовательские поля, только чтение: `kind` (`expression` \| `case`), `dataPath`, `title`, `detailExpression`, `totalExpression`, `casesCount` |
| `selection`, `filter`, `dataParameters`, `order`, `conditionalAppearance`, `outputParameters` | секции корня |
| `structure` | узлы структуры деревом |
| `hasAdditionalProperties` | `true` — в файле есть `additionalProperties` (переносится как есть) |
| `itemsViewMode`, `itemsUserSettingID`, `itemsUserSettingPresentation` | хвост корня настроек |

Секция — `{"items":[…]}` плюс хвост `viewMode`, `userSettingID`, `userSettingPresentation`; хвост при любой правке сохраняется. Элементы секций:

- выбранное поле (`selection`): `kind` (`field` \| `auto` \| `folder`), `use`, `field`, `title` (строка на языке конфигурации), `titleKind` — исходная форма заголовка в файле (`lws` — локализованная, `string` — простая), у папки `placement` и вложенные `items`, `viewMode`;
- элемент отбора (`filter`): `kind` (`comparison` \| `group`); у сравнения — `left`, `comparisonType`, `right` (массив значений: XSD допускает повторы, реальные у `NotInList`), `presentation`, `application`; у группы — `groupType` и вложенные `items`; у обоих хвост `viewMode`, `userSettingID`, `userSettingPresentation`;
- элемент сортировки (`order`): `kind` (`field` \| `auto`), `use`, `field`, `orderType` (`Asc` \| `Desc`), `autoOrder`, `distinctNullValues`, `viewMode`;
- значение параметра (`dataParameters`, `outputParameters`): `use`, `parameter`, `value` (массив, обычно из одного значения; `xsi:nil` → `[{"nil":true}]`), вложенные под-параметры `items` (имена с точкой, например `ТипДиаграммы.ВидПодписей`; только чтение), `viewMode`, `userSettingID`, `userSettingPresentation`;
- элемент условного оформления (`conditionalAppearance`): `use`, `fields` (поля `{use?, field}`), `filter` (элементы отбора), `appearance` (значения параметров оформления), `presentation`, `useIn` — заданные области использования (`group`, `hierarchicalGroup`, `overall`, `fieldsHeader`, `header`, `parameters`, `filter`, `resourceFieldsHeader`, `overallHeader`, `overallResourceFieldsHeader`; значения `Use` \| `DontUse`, отсутствие — умолчание платформы), хвост.

Узел структуры (`structure` корня и группировок, `rows`/`columns` таблицы, `points`/`series` диаграммы):

- общие ключи: `kind` (`group` \| `table` \| `chart` \| `nestedObject`), `use`, `name`, `viewMode`, `userSettingID`, `userSettingPresentation`;
- `group` — группировка (так же устроены группы строк, колонок, точек и серий): `groupFields`, `filter`, `order`, `selection`, `conditionalAppearance`, `outputParameters`, вложенный `structure`;
- `table`: `columns`, `rows`, `selection`, `conditionalAppearance`, `outputParameters`;
- `chart`: `points`, `series`, `selection`, `conditionalAppearance`, `outputParameters`;
- `nestedObject` — вложенный отчёт: только `objectID`, его настройки не раскрываются и не адресуются.

Поле группировки (`groupFields`) — всегда пятёрка: `field`, `groupType` (`Items` \| `Hierarchy` \| `HierarchyOnly`), `periodAdditionType` (`None`, `Year`, `Month`, …), `periodAdditionBegin` и `periodAdditionEnd` (границы — значения).

Типизированное значение (`Value`) — везде, где секции несут значения (`right` отбора, `value` параметров, `appearance` оформления, границы периода):

| Ключ | Содержимое |
|---|---|
| `type` | `xsi:type` дословно как в файле; пустая строка — элемент без типа |
| `text` | лексическое значение как в файле |
| `nil: true` | `xsi:nil="true"` |
| `decoded` | разобранное значение для показа: строка, число или булево |
| `period` | у `v8:StandardPeriod`: `{variant, startDate?, endDate?}` |
| `beginningDate` | у `v8:StandardBeginningDate`: `{variant, date?}` |
| `list` | у `v8:ValueListType`: `{items: [{value, presentation?}]}` |
| `attrs` | атрибуты `v8ui:Font`/`v8ui:Picture`/`v8ui:Line` по именам |
| `opaque: true` | тип вне белого списка записи: только чтение, правка — отказ |

### Адресация узлов

- Вариант адресуется по имени среди прямых детей корня: в операциях над самим вариантом — поле `name`, в операциях над содержимым — поле `variant`. Имя встречается в файле дважды — отказ.
- Узел структуры — `path` (у добавления — `parentPath` родителя): массив шагов `{"list": "…", "index": N}` от корня настроек, номера с нуля; пустой массив — сам корень. `structure` ведёт в узлы корня, группировок и групп строк/колонок/точек/серий, `rows`/`columns` — из таблицы, `points`/`series` — из диаграммы. Список, которого у вида узла нет, номер вне списка и путь внутрь вложенного отчёта — отказ.

### Мутации вариантов

Общие поля — `objectXml` и `schemaVersion`; сложные параметры — UTF-8 JSON в `payloadJson`.

| Операция (`apply-mutation`) | Вход кроме `objectXml`/`schemaVersion` | Поведение |
|---|---|---|
| `cf-dcs-add-settings-variant` | `name`, `payloadJson` `{presentation?}` (необязателен) | новый вариант в конец корня: имя, представление (по умолчанию равно имени) и пустые настройки, как пишет конфигуратор; отказ, если имя занято без учёта регистра (код конфигурации ищет вариант без учёта регистра) |
| `cf-dcs-remove-settings-variant` | `name` | вариант вырезается целыми строками |
| `cf-dcs-set-settings-variant-props` | `name`, `payloadJson` `{newName?, presentation?}` | переименование (занятое другим вариантом имя без учёта регистра — отказ, смена регистра своего имени — нет) и представление: замена, вставка по xs:sequence или снятие значением `null` |
| `cf-dcs-add-structure-item` | `variant`, `payloadJson` `{parentPath, list, index?, kind?, groupFields?}` | новый узел скаффолдом конфигуратора в позицию `index` коллекции (по умолчанию в конец); `kind` (`group` \| `table` \| `chart`) обязателен и допустим только при `list: "structure"` — у прочих списков вид предрешён |
| `cf-dcs-remove-structure-item` | `variant`, `payloadJson` `{path}` | узел вырезается целыми строками с потомками; пустой путь (корень настроек) — отказ |
| `cf-dcs-move-structure-item` | `variant`, `payloadJson` `{path, newIndex}` | байтовая перестановка строк в пределах своей коллекции; номер вне границ — отказ |
| `cf-dcs-set-group-fields` | `variant`, `payloadJson` `{path, items}` | поля группировки целиком, каждое — полной пятёркой `GroupItemField`; узел не группировка — отказ |
| `cf-dcs-set-selection` | `variant`, `payloadJson` `{path, items}` | выбранные поля целиком со сплайсом только изменённого |
| `cf-dcs-set-order` | `variant`, `payloadJson` `{path, items}` | сортировка целиком со сплайсом; у таблицы и диаграммы секции нет — отказ |
| `cf-dcs-set-filter` | `variant`, `payloadJson` `{path, items}` | отбор целиком со сплайсом: сравнения с повторяемым `right`, группы с вложенными `items` рекурсивно |
| `cf-dcs-set-parameter-value` | `variant`, `payloadJson` `{section, path?, parameter, value?, use?, remove?}` | точечная правка одного параметра секции `data` либо `output`: `use` и `value` меняются по отдельности (см. [«Флаг `use`»](#флаг-use-элементов-настроек)), прочее не трогается; отсутствующий параметр создаётся минимальным элементом (см. [«Порядок новых параметров вывода»](#порядок-новых-параметров-вывода)); `remove: true` вырезает элемент целиком; параметр вывода, которого уровень узла не хранит, — отказ ([корень](#параметры-вывода-группировки-в-корне-настроек), [группировка структуры](#параметры-вывода-которых-группировка-структуры-не-хранит), [таблица, диаграмма и их группы](#параметры-вывода-которых-не-хранят-таблица-диаграмма-и-их-группы)) |
| `cf-dcs-add-appearance-item` | `variant`, `payloadJson` `{path, index?, item}` | элемент условного оформления (`CAItem`) в позицию секции; `selection`, `filter` и `appearance` пишутся всегда, даже пустыми |
| `cf-dcs-set-appearance-item` | `variant`, `payloadJson` `{path, index, item}` | замена элемента целиком; неизменённые вложенные элементы и значения переносят исходные байты |
| `cf-dcs-remove-appearance-item` | `variant`, `payloadJson` `{path, index}` | элемент вырезается; опустевшая секция без собственного хвоста снимается |

Неизвестный ключ payload — отказ.

#### Флаг `use` элементов настроек

`use=true` — умолчание, и платформа его не хранит: записанный `<dcscor:use>true</dcscor:use>` загрузка отбрасывает, а `use=false` сохраняет. Поэтому все писатели настроек пишут `use` только значением `false`:

- `use: true`, как и отсутствие ключа, элемента `use` не пишет;
- `cf-dcs-set-parameter-value` с `use: true` снимает записанный `use=false` целой строкой; у элемента без `use` файл не меняется;
- в сплайсе и при замене элемента оформления `use: true` равен отсутствию `use`, поэтому эхо — байтовый no-op;
- записанный в файле `use=true` читается как есть, и эхо его не трогает. `use: false` пишется явно.

`cf-dcs-set-parameter-value`: параметры данных есть только у корня настроек (`section: "data"` с непустым `path` — отказ); под-параметры (имя с точкой) — только чтение. Скаляры принимаются без обёртки и пишутся `xs:string`/`xs:decimal`/`xs:boolean`; явный `value: null` пишет `xsi:nil`: в формате значение параметра присутствует всегда. Отсутствующий в payload `value` значение не трогает. Значение, глубоко равное прочитанному, не переписывается, см. [«Значения: белый список записи»](#значения-белый-список-записи).

### Порядок новых параметров вывода

Платформа хранит параметры вывода в постоянном порядке и сама сортирует их при загрузке. Поэтому `cf-dcs-set-parameter-value` с `section: "output"` ставит **отсутствующий** параметр перед первым записанным параметром с большим рангом, на любом уровне узла.

| Ранг | Параметры |
|---|---|
| 1–4 | `МакетОформления`, `КоличествоЗаписей`, `ПроцентЗаписей`, `ТипМакета` |
| 5–9 | `РасположениеИтогов`, `РасположениеПолейГруппировки`, `РасположениеГруппировки`, `РасположениеРеквизитов`, `РасположениеРесурсов` |
| 10–11 | `ГоризонтальноеРасположениеОбщихИтогов` = `РасположениеОбщихИтогов`, `ВертикальноеРасположениеОбщихИтогов` |
| 12–13 | `ТипЗаголовкаПолей`, `ТипДиаграммы` |
| 14–17 | `ВыводитьЗаголовок`, `Заголовок`, `ВыводитьПараметрыДанных`, `ВыводитьОтбор` |
| 18–20 | `АвтоПозицияРесурсов`, `ФиксацияСлева`, `ВариантИспользованияГруппировки` = `ФиксацияСверху` |

- Имена через «=» делят ранг: новый встаёт после уже записанного соседа того же ранга. Оба имени такой пары платформа не хранит вместе ни на одном уровне (см. разделы ниже), поэтому строгий порядок внутри пары не нужен.
- Существующие параметры не переставляются; имена вне таблицы при поиске позиции пропускаются. `remove: true` только что добавленного параметра возвращает файл байт в байт, в том числе у самозакрытого узла ([«Сплайс только изменённого»](#сплайс-только-изменённого)).
- Новое имя вне таблицы и новый параметр данных (`section: "data"`) встают в конец секции.

Примеры: новый `РасположениеИтогов` встаёт перед записанным `Заголовок`; `ТипДиаграммы` — перед `ВыводитьЗаголовок`, `Заголовок`, `ВыводитьПараметрыДанных` и `ВыводитьОтбор`; `ТипЗаголовкаПолей` — перед записанным `ТипДиаграммы`, `АвтоПозицияРесурсов` — перед записанным `ФиксацияСлева`.

### Параметры вывода группировки в корне настроек

Пять параметров вывода — `КоличествоЗаписей`, `ПроцентЗаписей`, `ТипМакета`, `РасположениеОбщихИтогов` и `ВариантИспользованияГруппировки` — платформа в корне настроек варианта не хранит: загрузка принимает их без ошибки, но молча отбрасывает; остальные 17 имён таблицы рангов в корне хранятся.

Поэтому `cf-dcs-set-parameter-value` с `section: "output"` и пустым `path`, который создал бы или изменил такой параметр в корне, — отказ: «Параметр вывода «КоличествоЗаписей»: платформа не хранит этот параметр вывода в корне настроек; задайте его у группировки.» У `РасположениеОбщихИтогов` подсказка другая — «задайте его у группы строк таблицы»: у группировки структуры он тоже не хранится ([ниже](#параметры-вывода-которых-группировка-структуры-не-хранит)). Эхо элемента, записанного в корень, файл не меняет и отказом не считается, `remove: true` его снимает. Ниже корня действуют запреты своего уровня (разделы ниже). Параметры данных с теми же именами правилу не подчиняются.

### Параметры вывода, которых группировка структуры не хранит

У группировки структуры (`dcsset:item xsi:type="dcsset:StructureItemGroup"`) платформа не хранит пять параметров вывода — `ФиксацияСверху`, `ФиксацияСлева`, `ВыводитьПараметрыДанных`, `РасположениеОбщихИтогов` и `ГоризонтальноеРасположениеОбщихИтогов`: загрузка принимает их без ошибки и молча отбрасывает; остальные 17 имён таблицы рангов у группировки хранятся.

Поэтому `cf-dcs-set-parameter-value` с `section: "output"`, который создал бы или изменил такой параметр у группировки структуры, — отказ: «Параметр вывода «ФиксацияСверху»: платформа не хранит этот параметр вывода у группировки структуры; задайте его в корне настроек.», у `РасположениеОбщихИтогов` — «…в корне настроек он тоже не хранится, задайте его у группы строк таблицы.». Эхо записанного элемента и `remove: true` допустимы, как у запрета в корне.

- **Какие узлы.** Группировка структуры — узел, до которого путь доходит одними шагами `structure`, на любой глубине: вложенная группировка хранит то же, что верхняя.
- **Каких узлов запрет не касается.** Таблица, диаграмма, группы строк, колонок, точек и серий и их вложенные группы (`dcsset:item` без `xsi:type` за шагами `rows`, `columns`, `points`, `series`): у них свои запреты — см. [следующий раздел](#параметры-вывода-которых-не-хранят-таблица-диаграмма-и-их-группы). XSD набор имён не ограничивает: секции всех видов узлов — пустые расширения `ParameterValues`.

### Параметры вывода, которых не хранят таблица, диаграмма и их группы

У таблицы, диаграммы, группы строк, группы колонок, группы точек и группы серий платформа хранит только часть из 22 имён таблицы рангов, остальные загрузка молча отбрасывает. Группы строк и колонок устроены одинаково, группы точек и серий тоже.

| Уровень | Какие узлы | Не хранит | Хранит |
|---|---|---|---|
| таблица | `StructureItemTable` | 10: `ФиксацияСверху`, `ФиксацияСлева`, `ВариантИспользованияГруппировки`, `ВыводитьОтбор`, `ВыводитьПараметрыДанных`, `ТипДиаграммы`, `РасположениеОбщихИтогов`, `ТипМакета`, `ПроцентЗаписей`, `КоличествоЗаписей` | 12: `МакетОформления`, `РасположениеИтогов`, `РасположениеПолейГруппировки`, `РасположениеГруппировки`, `РасположениеРеквизитов`, `РасположениеРесурсов`, `ГоризонтальноеРасположениеОбщихИтогов`, `ВертикальноеРасположениеОбщихИтогов`, `ТипЗаголовкаПолей`, `ВыводитьЗаголовок`, `Заголовок`, `АвтоПозицияРесурсов` |
| группа таблицы | группа, путь к которой проходит шагом `rows` или `columns`: группа строк, колонок и их вложенные группы | 7: `ФиксацияСверху`, `ФиксацияСлева`, `ВыводитьПараметрыДанных`, `ТипДиаграммы`, `ВертикальноеРасположениеОбщихИтогов`, `ГоризонтальноеРасположениеОбщихИтогов`, `ТипМакета` | 15: остальные, в том числе `РасположениеОбщихИтогов` — он хранится только здесь |
| диаграмма | `StructureItemChart` | 19: все, кроме трёх хранимых | 3: `ТипДиаграммы`, `ВыводитьЗаголовок`, `Заголовок` |
| группа диаграммы | группа, путь к которой проходит шагом `points` или `series`: группа точек, серий и их вложенные группы | 20: все, кроме двух хранимых | 2: `КоличествоЗаписей`, `ПроцентЗаписей` |

Поэтому `cf-dcs-set-parameter-value` с `section: "output"`, который создал бы или изменил такой параметр на этом уровне, — отказ, как в корне и у группировки структуры; текст называет уровень и где параметр хранится: «Параметр вывода «ТипМакета»: платформа не хранит этот параметр вывода у таблицы; он хранится только у группировки структуры.», «Параметр вывода «ТипДиаграммы»: платформа не хранит этот параметр вывода у группы строк или колонок таблицы; он хранится в корне настроек, у группировки структуры и у диаграммы.» Эхо записанного элемента и `remove: true` допустимы, правка его значения или `use` — отказ.

- **Множества явные.** В запретах только имена, которые загрузка отбрасывает; имена вне таблицы рангов запись на этих уровнях не ограничивает.
- **Вложенные группы.** Вложенные в группы строк, колонок, точек и серий группы (`dcsset:item` без `xsi:type`) получают запрет своей верхней группы.
- **Пары равного ранга.** Ни на одном уровне платформа не хранит оба имени пары: у таблицы из пар остаётся только `ГоризонтальноеРасположениеОбщихИтогов`, у групп таблицы — `РасположениеОбщихИтогов` и `ВариантИспользованияГруппировки`, у диаграммы и её групп — ни одного.
- **Другие пути записи.** Параметры вывода пишет только `cf-dcs-set-parameter-value`; `cf-dcs-add-structure-item` пишет узлы без них, `cf-dcs-move-structure-item` уровень узла не меняет.

### Сплайс только изменённого

`set`-операции секций принимают список элементов целиком, но файл правится точечно: элементы запроса, глубоко равные прочитанным, переносят исходные байты и занимают позицию по порядку запроса; новые и изменённые пишутся заново; снятые вырезаются; хвост секции остаётся на месте. Пустой `items` снимает секцию целиком, если у неё нет собственного хвоста. Эхо прочитанного (ответ `cf-dcs-settings-info` без изменений) не меняет файл байт в байт.

Первый ребёнок пустого узла раскрывает его самозакрытый тег, а снятие последнего (секции, параметра вывода, элемента оформления, узла структуры) сворачивает узел обратно в `<x …/>`: так платформа пишет пустые узлы. Поэтому добавление и снятие того же у пустой таблицы возвращает файл байт в байт. Узел сворачивается, только если между его тегами одни пробельные символы.

Новое пишется по образцам конфигуратора и строго на место по xs:sequence вида узла (`column` перед `row`, `point` перед `series`, узлы структуры после `outputParameters` до хвоста):

- новый вариант — имя, представление `v8:LocalStringType` языком конфигурации и самозакрытый `dcsset:settings` с объявлениями пространств имён формата файла;
- новая группировка — `groupItems` полной пятёркой на каждое поле (без `groupFields` — «детальные записи» без `groupItems`), порядок с `OrderItemAuto` и выбор с `SelectedItemAuto`; новые строка, колонка, точка и серия — так же; вложенная группа строки/колонки/точки/серии — `dcsset:item` без `xsi:type`; таблица и диаграмма — пустые самозакрытые элементы;
- заголовки и представления — строкой языка конфигурации; исходная простая форма заголовка (`titleKind: "string"`) у неизменённых элементов сохраняется.

### Значения: белый список записи

Писать можно значения типов `xs:string`, `xs:boolean`, `xs:decimal`, `xs:dateTime`, `dcscor:Field`, `dcscor:DesignTimeValue` (текст passthrough), `v8:LocalStringType` (строка языка конфигурации), `v8:StandardPeriod`, `v8:StandardBeginningDate`, `v8:ValueListType` (элементы из простых скаляров; у параметра схемы список пишется повторяющимися `value` без представлений — см. [«Запись типа значения»](#запись-типа-значения)), перечисления `dcsset:*`/`dcscor:*`, `v8ui:Color` и тип диаграммы `v8ui:ChartType`. Прочие — `v8ui:Font`, `v8ui:Picture`, `v8ui:Line`, другие типы `v8ui:*` (например, `v8ui:ChartLabelType`), типы с нестабильными префиксами (например, `d8p1:ChartSplineMode`) и всё неопознанное — читаются с `opaque: true` и переносятся только дословно: неизменённое значение переживает правку соседей, его правка — отказ.

**Пустая строка языка.** Пустой `v8:LocalStringType` платформа хранит самозакрытым элементом без `v8:item` (`<dcscor:value xsi:type="v8:LocalStringType"/>`). Чтение отдаёт его как `{"type": "v8:LocalStringType"}` без `decoded`; запись пишет той же формой и его, и `{"type": "v8:LocalStringType", "decoded": ""}`. Правило действует для всех значений настроек: параметров данных и вывода, оформления, правого значения отбора. Значение без `decoded`, но с ключами других типов (`text`, `period`, `beginningDate`, `list`), отвергается.

Значение параметра оформления, глубоко равное прочитанному у параметра с тем же именем, при замене элемента оформления переносится дословно: правка `use` у «Текста» на нескольких языках сохраняет все языки. Значения только для чтения (`opaque`, `attrs`) так не переносятся, их правку отвергает писатель. Эхо значения параметра данных и вывода элемент не переписывает, поэтому сохраняются строка на нескольких языках, форма «только en» и пустой `v8:content`; настоящая правка текста пишет одну строку языка конфигурации.

**Тип диаграммы.** Параметр вывода `ТипДиаграммы` несёт значение `v8ui:ChartType`; мастер настроек пишет его в корневые `outputParameters` варианта, правится он и в узле диаграммы. Значение — лексема перечисления: `{"type": "v8ui:ChartType", "text": "Pie3D"}` (как читается из файла) или та же лексема в `decoded`. Допустимы 47 значений `ChartType` из XSD `data-ui`, одинаковые в форматах 2.10–2.21. Незнакомая лексема, лексема другим регистром (`column`) и значение без лексемы — отказ «Тип диаграммы (v8ui:ChartType) пишется лексемой перечисления формата…»: перечитка моделью незнакомую лексему пропускает, а строгая `cf-dcs-validate` такой файл отвергает. Чтение отдаёт значение без `opaque`. Под-параметры `ТипДиаграммы.*` (например, `ТипДиаграммы.ВидПодписей` типа `v8ui:ChartLabelType`) только читаются: при смене типа диаграммы они переносятся байтами исходника.

```json
{"op": "cf-dcs-set-parameter-value", "objectXml": "…", "schemaVersion": "V2_20", "variant": "Основной",
 "payloadJson": "{\"section\":\"output\",\"path\":[],\"parameter\":\"ТипДиаграммы\",\"value\":{\"type\":\"v8ui:ChartType\",\"text\":\"Column\"}}"}
```

### Ограничения правки вариантов

- Пользовательские поля (`userFields`) — только чтение.
- Вложенный отчёт (`nestedObject`) — адресуется как узел (его можно удалить или переставить), но путь внутрь не заходит: настройки вложенного отчёта не раскрываются и не правятся. Вложенные схемы и их варианты из корня не видны.
- Под-параметры (имена с точкой, вложенные `items` значений параметров) — только чтение.
- Значения типов вне белого списка записи (`opaque: true`) — только чтение и дословный перенос.
- `userSettingID` и `userSettingPresentation` неприкосновенны: переносятся как даны, не генерируются и не меняются; `iID` не пишется никогда.

## Автозаполнение полей по запросу

`cf-dcs-autofill-fields` (`apply-mutation`) заполняет поля набора-запроса по списку выборки текста его запроса. Вход: `objectXml`, `schemaVersion`, `dataSet` — имя набора верхнего уровня либо путь `Объединение/Вложенный` (адресация та же, что у `cf-dcs-set-query`; путь к объединению — отказ: его поля собираются из вложенных наборов); набор обязан быть запросом с непустым текстом, иначе отказ.

Разбирается только текст запроса, типы из метаданных не выводятся: новое поле получает лишь `dataPath` и `field`, тип задаётся `cf-dcs-set-field` с `valueType`. По той же причине `ВЫБРАТЬ *` — отказ: звёздочку разворачивает платформа.

Разбор идёт по правилам языка запросов (русские и английские ключевые слова равноправны):

- берётся последний запрос пакета, который является выборкой: начинается с `ВЫБРАТЬ`/`SELECT` и не пишет во временную таблицу (нет `ПОМЕСТИТЬ`/`INTO` и `ДОБАВИТЬ` верхнего уровня); `УНИЧТОЖИТЬ` пропускается. Запросы пакета делит `;` верхнего уровня (вне строк, комментариев, скобок и блоков `{…}`); пакет без запроса выборки — отказ. У объединения берётся первый запрос; список выборки читается от `ВЫБРАТЬ`/`SELECT` до следующего предложения верхнего уровня: `ИЗ`/`FROM`, `ПОМЕСТИТЬ`/`INTO`, `ОБЪЕДИНИТЬ`/`UNION`, а у запроса без источника (`ВЫБРАТЬ NULL КАК Поле ГДЕ ЛОЖЬ`) — `ГДЕ`, `СГРУППИРОВАТЬ`, `ИМЕЮЩИЕ`, `УПОРЯДОЧИТЬ`, `АВТОУПОРЯДОЧИВАНИЕ`, `ИТОГИ`, `ИНДЕКСИРОВАТЬ`, `ДЛЯ ИЗМЕНЕНИЯ` и их английские пары. Слово из этого списка остаётся именем, а не границей, если оно стоит после точки или `&` (`Т.Итоги`, `&Где`), сразу после `КАК`/`AS` (`Т.Код КАК Итоги`, `AS Order`), перед точкой (алиас таблицы: `Итоги.Ссылка … КАК Итоги`) или если у предложения из двух слов нет второго (`СГРУППИРОВАТЬ ПО`, `УПОРЯДОЧИТЬ ПО`, `ИНДЕКСИРОВАТЬ ПО`, `ДЛЯ ИЗМЕНЕНИЯ` и `GROUP BY`, `ORDER BY`, `INDEX BY`, `FOR UPDATE` — границей служит только пара);
- строки `"…"` (с экранированной `""`), комментарии `//…` и вложенные скобки не рвут выражения: записи делят только запятые верхнего уровня; блок `{…}` расширения языка запросов СКД пропускается целиком;
- префиксы выборки `РАЗЛИЧНЫЕ`/`DISTINCT`, `РАЗРЕШЕННЫЕ`/`ALLOWED` и `ПЕРВЫЕ`/`TOP` с числом записей полей не называют и пропускаются;
- имя поля — псевдоним после последнего `КАК`/`AS` верхнего уровня записи; без псевдонима — имя колонки пути, как его даёт платформа: сегменты после алиаса таблицы склеиваются (`Т.Поле` — `Поле`, `Т.Автор.Наименование` — `АвторНаименование`). Первый сегмент пути всегда считается алиасом таблицы (источники по тексту не определить), поэтому `Автор.Наименование` без алиаса даёт `Наименование`; выражение без псевдонима и пути попадает в `skipped` с причиной.

Добавляются только недостающие поля: колонка уже есть, если у набора есть поле с таким `field` **или** таким `dataPath` (путь к данным поля может отличаться от колонки). Сравнение без учёта регистра, повторы имён в выборке схлопываются так же. Новые `DataSetFieldField` с равными `dataPath` и `field` встают после существующих полей набора; существующие поля не меняются, ничего не удаляется. Когда добавлять нечего, файл не пишется: повтор операции — байтовый no-op.

У вложенного набора объединения добавленные колонки дописываются и в поля каждого объединения над ним, если у объединения такой колонки ещё нет (по `dataPath` или `field`, без учёта регистра): так список полей объединения ведёт конфигуратор. Поле встаёт после полей объединения, перед вложенными наборами; прочие поля не трогаются.

Ответ — не `OK`, а JSON: `{"added": […], "skipped": [{"expression", "reason"}]}` — добавленные пути в порядке выборки и пропущенные выражения с причинами; если колонки дописаны в объединения, ещё `"unions": [{"dataSet": "Объединение", "added": […]}]` (путь объединения, сверху вниз).

```json
{"op": "cf-dcs-autofill-fields", "objectXml": "…/Ext/Template.xml", "schemaVersion": "V2_20",
 "dataSet": "ОсновнойЗапрос"}
```

## Строгая проверка схемы

`cf-dcs-validate` с параметром `strict: true` (`read-json`) проверяет файл по XSD СКД и выполняет JAXB-чтение. Набор XSD и модель выбираются по `schemaVersion`. Для `Template.dcs` без явной версии берётся `Runtime-Version` проекта 1С:EDT, для отдельного файла EDT без манифеста используется последний формат. Ответ: `{"ok": true|false, "errors": [{"message", "line"?, "column"?}], "warnings": [{"message", "parameter"?, "dataSet"?, "link"?, "kind"}]}` со всеми найденными несоответствиями. Без `strict` — JAXB-чтение моделью формата `schemaVersion` с ответом `{"valid":…}`, без предупреждений; в 2.10–2.11 модели СКД нет, ответ `{"valid": false, "error": "Схема компоновки данных в формате 2.10 не поддержана: в XSD этого формата нет полного набора схем СКД."}` (см. [«Ограничения»](#ограничения)).

Предупреждения на `ok` не влияют: схема с ними читается и загружается. Вид предупреждения — в ключе `kind`; сначала идут параметры запросов, затем списки значений, затем связи наборов:

| `kind` | О чём | Ключи |
|---|---|---|
| `undeclaredQueryParameter` | `&`-параметр текста запроса не объявлен в схеме | `message`, `parameter`, `dataSet`, `kind` |
| `valueListPresentationsLost` | список значений параметра схемы элементом `v8:ValueListType`, чьи представления потеряет загрузка в платформу | `message`, `parameter` (имя параметра схемы), `kind` |
| `linkListFlagWithoutParameter` | связь наборов с флагом «Список параметров» без параметра связи: загрузка флаг отбросит | `message`, `link` (порядковый номер связи в файле с нуля, как `index` у `cf-dcs-set-link`), `kind` |

**Необъявленные параметры запросов** (`undeclaredQueryParameter`) — `&`-параметры текстов запросов, не объявленные в параметрах схемы: «параметр запроса &X не объявлен в схеме (набор данных Y)», `dataSet` — путь набора (`Объединение/Вложенный` у вложенного). Платформа объявляет такие параметры сама, правка текста мимо конфигуратора (например, `cf-dcs-set-query`) их не добавляет, и отчёт такой параметр не заполнит. Учитываются параметры всех наборов-запросов, включая вложенные в объединения, и внутри блоков `{…}` расширения языка запросов; параметры в строках `"…"` и комментариях `//…` — нет; имена сравниваются без учёта регистра. Объявленным считается и параметр связи наборов (`dataSetLink/parameter`).

**Списки значений элементом `v8:ValueListType`** (`valueListPresentationsLost`). Платформа хранит список значений параметра схемы повторяющимися `value` без представлений: список, записанный одним элементом `<value xsi:type="v8:ValueListType">` с представлениями элементов, загрузка разворачивает и молча теряет представления ([«Значение параметра: valueTyped»](#значение-параметра-valuetyped)). Строгая проверка называет параметры, где это случится.

- **Когда.** Параметр корня схемы с `valueListAllowed: true`, у которого значение — элемент `v8:ValueListType` и хотя бы у одного элемента непустое представление. В `cf-dcs-info` признак тот же: `valueListAllowed: true` и непустое `presentation` хотя бы у одного элемента `valueTyped.list.items`.
- **Текст** — например: «параметр схемы Валюта: список значений записан старой формой v8:ValueListType с представлениями элементов (USD: «Доллар», EUR: «Евро»); при загрузке платформа развернёт его в отдельные значения, а представления потеряет; уберите представления или оставьте список как есть, если их потеря не важна». Называются три первых элемента с представлениями (значение — текстом, «не задано» у `xsi:nil`, «пустая строка», вариант периода), остальные — числом: «… и ещё 2».
- **Что делать.** Записать список заново (`cf-dcs-set-parameter` с `value` без `presentation`): он ляжет формой платформы, и предупреждение уйдёт. Или оставить как есть: эхо и правка других свойств параметра элемент не меняют. Снятие `valueListAllowed` убирает предупреждение, но представления в файле остаются.
- **Не предупреждается.** Элемент `v8:ValueListType` без представлений: платформа развернёт его без потерь. Тот же элемент у параметра без `valueListAllowed: true`. Списки значений в вариантах настроек (правое значение отбора, значения параметров данных и вывода): там платформа хранит `v8:ValueListType` как есть. Параметры вложенных схем: они только читаются.

**Флаг списка без параметра связи** (`linkListFlagWithoutParameter`). У связи без `parameter` загрузка отбрасывает записанный `parameterListAllowed` и с `false`, и с `true` ([«Связи наборов»](#связи-наборов)). Запись такой флаг не пишет, но в файле он бывает; строгая проверка называет такую связь.

- **Когда.** У связи корня схемы есть `parameterListAllowed` (любое значение), а `parameter` нет или он пустой. Связи вложенных схем только читаются, правило их не касается.
- **Текст** — например: «связь наборов ОсновнойЗапрос → Остатки (номер 1): флаг «Список параметров» (parameterListAllowed=true) записан без параметра связи; при загрузке платформа его отбросит. Задайте parameter или снимите флаг».
- **Что делать.** Задать `parameter` (флаг у связи с параметром хранится) или снять флаг: `parameterListAllowed: null` (у записанного `true` — и `false`).

Схемы XDTO описывают модель, а не файлы выгрузки, поэтому проверка идёт с поправками «как пишет платформа» (в памяти, `DcsXsdShims`):

- корень: платформа и 1С:EDT пишут `DataCompositionSchema`, XSD объявляет `dataCompositionSchema` — объявление переименовывается;
- `NestedDataCompositionSchema`: `URL` необязателен (вложенная схема пишется телом, без `URL`);
- `GroupTemplate`: вместо одиночного `xs:choice` XDTO — свойства подряд в объявленном порядке, каждое необязательно (`groupName`, `templateType` и `template` вместе);
- `ValueListType` (`data/core`): так же вместо одиночного `xs:choice`; `lastId` — `xs:decimal`, потому что платформа пишет `xsi:type="xs:decimal"`, который от объявленного `xs:long` не выводится;
- `ExpressionAreaTemplateParameter`: `expression` необязателен (пустое выражение параметра области не пишется);
- в набор схем добавлен `data/enterprise`: его перечисления (`FoldersAndItemsUse`, `LinkedValueChangeMode`) платформа пишет в `xsi:type` значений настроек, хотя схемы СКД это пространство не импортируют;
- значения с `xsi:type` из пространств, схем которых в коллекции нет и быть не может (типы конфигурации `data/enterprise/current-config`, диаграммы `8.2/data/chart`, цвета и стили `data/ui/colors/*`, `data/ui/style`), проверяются как непрозрачные: содержимое такого значения не проверяется. Опечатка в типе известного пространства остаётся ошибкой.

## Создание и удаление макета

Операции над макетом СКД целиком работают не с файлом схемы, а с его владельцем: `objectXml` — описание владельца (`Reports/Отчет1.xml`, `DataProcessors/….xml` и любой другой вид с макетами по модели формата, внешние отчёт и обработка; `Configuration.xml` — общий макет; в проекте 1С:EDT — `.mdo` владельца или `Configuration.mdo`).

### cf-dcs-template-add

Вход: `objectXml`, `schemaVersion`, `name` и необязательный `makeMain`. Создаёт макет «как конфигуратор»:

- `Templates/<Имя>.xml` — описание по канону cf-dcs (`<Synonym/><Comment/>`, `TemplateType` = `DataCompositionSchema`); UUID детерминированные, как у остальных scaffold: та же правка того же владельца даёт те же идентификаторы;
- `Templates/<Имя>/Ext/Template.xml` — байты эталона платформы (BOM, CRLF, табы, без перевода строки в конце): пустая схема с одним вариантом настроек `Основной`, объявления у его настроек - формата выгрузки;
- строка `<Template>` в `ChildObjects` владельца — на место по порядку видов узлов модели формата; пустой `<ChildObjects/>` раскрывается;
- общий макет (владелец — `Configuration.xml`): `CommonTemplates/<Имя>{.xml,/Ext/Template.xml}`, `<CommonTemplate>` в составе конфигурации по его порядку видов и синхронизация `ConfigDumpInfo.xml`;
- `makeMain: true` — заполнить `MainDataCompositionSchema` владельца ссылкой `<Вид>.<ИмяВладельца>.Template.<Имя>`: существующий элемент заменяется на месте, отсутствующий встаёт по месту свойства в sequence формата. Допустим только у видов, имеющих это свойство (отчёт, внешний отчёт), иначе отказ.

Проект 1С:EDT: блок `<templates uuid>` в `.mdo` владельца и `Templates/<Имя>/Template.dcs` с тем же эталоном, но без BOM; пустой синоним не пишется. Переводы строк `Template.dcs` - как у `.mdo`, рядом с которым он встаёт (у общего макета - как у `Configuration.mdo`). Общий макет — `src/CommonTemplates/<Имя>/<Имя>.mdo` с `Template.dcs` и ссылка в `Configuration.mdo`; `makeMain` — свойство `mainDataCompositionSchema` в `.mdo`.

Макет создаётся во всех форматах выгрузки. Описание берётся из канона и проецируется в формат файла, содержимое схемы берётся из канона.

Отказы: невалидное имя (общий валидатор имён), имя занято любым макетом — файлом описания, каталогом содержимого или записью состава, вид владельца без макетов, `makeMain` у вида без свойства, объект заперт правилами поддержки поставщика. Отказ состава не оставляет файлов макета без ссылки: владелец проверяется моделью формата до записи на диск.

### cf-dcs-template-remove

Вход: `objectXml` владельца, `name`. Удаляет описание макета, каталог содержимого и строку состава (опустевший `ChildObjects` сворачивается в `<ChildObjects/>`, как его пишет платформа); `MainDataCompositionSchema`, указывавший на макет, пустеет — `<MainDataCompositionSchema/>` (в EDT свойство уходит: пустым 1С:EDT его не пишет).

Отказы: макета нет (файлом или записью состава); `TemplateType` описания не `DataCompositionSchema` — «не схема компоновки данных: удалите его средствами платформы»; макет заперт своим правилом поддержки (разрешение на владельца его не открывает).

Переименования макета нет: за именем макета тянется каскад по ссылкам форм и настроек — переименовывайте средствами платформы.

```json
{"op": "cf-dcs-template-add", "objectXml": "…/Reports/Отчет1.xml", "schemaVersion": "V2_20",
 "name": "СхемаОстатков", "makeMain": true}
```

## Пакеты операций

Составные правки редактора идут одним пакетом `apply-mutation` `{"op": "batch", "operations": […]}` — общим механизмом сеанса записи ([write-session.md](write-session.md#пакет-операций)). Операции `cf-dcs-*` в пакете отвечают и отказывают так же, как без него. Так пишут:

- мастер настроек — снять корневые узлы структуры, выбранные поля и порядок корня, цепочка `cf-dcs-add-structure-item`, свой выбор `[{kind: "auto"}]` у диаграммы, `ТипДиаграммы` в корневых параметрах вывода; при смене одних полей группировки — `cf-dcs-set-group-fields` вместо удаления и добавления, чтобы сохранить `userSettingID` узла;
- конструктор запроса — `cf-dcs-set-query`, затем `cf-dcs-add-parameter` на каждый `&`-параметр текста, не объявленный в схеме, затем `cf-dcs-autofill-fields` у набора с автозаполнением. Тип нового параметра не задаётся (см. [«Параметры»](#параметры)).

Правила пакета для схем компоновки:

- **Каждая операция видит правки предыдущих.** Операции идут по порядку в одном сеансе, поэтому номера в `path`/`parentPath` считаются по состоянию после предыдущих операций: удаления корневых узлов идут по индексу 0, путь вложенного добавления известен заранее.
- **Атомарность.** Первый отказ отменяет весь пакет: следующие операции не выполняются, диск не меняется, stdout пуст, код выхода 2, в stderr — «Операция N (имя): причина» с номером от единицы.
- **`dryRun` у пакета** проверяет всё без записи и отвечает тем же массивом, что настоящий запуск.
- **Ответ** — JSON-массив ответов операций строками в их порядке: `"OK"` у правок, у `cf-dcs-autofill-fields` — JSON `{added, skipped}` строкой.
- **«В новый вариант…»** — первой операцией `cf-dcs-add-settings-variant` с новым именем, дальше операции, у которых `variant` равен этому имени. Прочие варианты не трогаются, новый встаёт в конец корня.
- **Круговая пересборка — байт в байт.** Если снять корневые узлы и добавить их заново из прочитанных DTO, а выбранные поля и порядок корня передать прочитанными, то у структуры, которую строит мастер, файл совпадает с исходным байт в байт. Под-параметры `ТипДиаграммы.*` и `userSettingID` узлов пакет не воспроизводит, поэтому мастер пересобирает только изменённое.

## Проект 1С:EDT

Схема в проекте 1С:EDT (`Template.dcs`) — тот же XML, что в выгрузке конфигуратора, поэтому чтение и все мутации работают по пути к `.dcs`. `schemaVersion` задаёт вызывающая программа по `Runtime-Version` в `DT-INF/PROJECT.PMF`. Схема объекта, запертого правилами поддержки поставщика, не правится. Макет создаётся и удаляется по `.mdo` владельца.

## Ограничения

- Вложенные схемы (`nestedSchemas`) и макеты областей читаются только списком имён и не правятся. Ограничения правки вариантов настроек — в разделе [«Ограничения правки вариантов»](#ограничения-правки-вариантов).
- Макет СКД создаётся и удаляется целиком, переименования нет ([«Создание и удаление макета»](#создание-и-удаление-макета)).
- Папки полей и поля-вложенные наборы читаются (`kind` = `folder` | `nested`), но не правятся.
- Оформление и параметры ввода полей, доступные значения и параметры выбора параметров — только чтение (`hasAppearance`, `hasInputParameters`, `hasAvailableValues` — признаки наличия). Тип значения поля вложенного набора объединения и типы внутри вложенных схем — только чтение.
- Порядок элементов составного типа запись не переставляет: после загрузки платформа может выгрузить их в своём порядке ([«Запись типа значения»](#запись-типа-значения)).
- Флаг `autoFillFields` исполняет платформа; `cf-dcs-autofill-fields` разбирает только текст запроса и типов полей не выводит ([«Автозаполнение полей по запросу»](#автозаполнение-полей-по-запросу)).
- `cf-dcs-set-query` пишет готовый текст с приведением переводов строк. Синтаксис запроса проверяет платформа.
- Новый параметр данных встаёт в конец секции ([«Порядок новых параметров вывода»](#порядок-новых-параметров-вывода)).
- В форматах 2.10 и 2.11 чтение и правка схемы не работают. Работают чтение настроек и словаря типов, создание и удаление макета.
